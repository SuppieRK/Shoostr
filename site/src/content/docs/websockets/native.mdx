## Description

Choose the native `routes.websocket(...)` overload when you need a Jetty `Session.Listener`, explicit demand,
subprotocol selection or connection limits. Call `Session.demand()` to let Jetty deliver the next event to a
listener that uses explicit demand. For sequential application callbacks on complete messages, use
[managed WebSockets](../managed/).

The factory runs during HTTP admission and creates a fresh listener for each accepted connection. Copy any path
or identity values the listener needs before the factory returns. Keep the live handshake request and upgrade
response within that callback.

Jetty can reuse the binary receive buffer as soon as you complete the `Callback` passed to
`onWebSocketBinary(...)`. Copy any bytes you need to keep before completing it.
For asynchronous replies, see [Jetty's server endpoint guide](https://jetty.org/docs/jetty/12.1/programming-guide/server/websocket.html#jetty-endpoints)
and the [send and demand rules shared by clients and servers](https://jetty.org/docs/jetty/12.1/programming-guide/client/websocket.html#architecture).

## Example

The factory for `/native/{room}` checks the handshake before creating the listener.

1. Require exactly one `Origin` header with the value `https://app.example`. Throw `ForbiddenException` to return
   `403` if the check fails.
2. Require the client to offer `chat.v2`. Throw `BadRequestException` to return `400` if it is missing.
3. Select `chat.v2`, then create the listener with a prefix built from the captured room name.

Shoostr skips HTTP CORS and CSRF for recognized WebSocket routes. Use the Origin check for browser admission.
Authenticate private endpoints separately from the Origin check and subprotocol selection.

When the session opens, the listener limits incoming text and binary messages to 64 bytes each. For text,
the limit counts UTF-8 bytes. Jetty allows up to two outgoing data frames to wait for sending. If external
producers send concurrently, bound their pending work and serialize their writes.

The listener calls `demand()` on open. It prefixes text replies with the room name and copies binary input
before acknowledging receipt, so the echo can use its own bytes. After a successful write, the listener
calls `demand()` again. If the write fails, it disconnects the session. Jetty owns the session and releases
its transport resources when the connection or application closes.

To enable HTTP/2 WebSockets, call `options.setHttp2(true)` before constructing the application. HTTP/1.1
`GET` upgrades are still available.

- On HTTP/2, Shoostr runs the handshake for extended `CONNECT` with the `websocket` protocol. Ordinary
  `CONNECT` follows ordinary HTTP routing.
- Register WebSocket routes the same way for both transports. Shoostr looks up the route with `GET` and
  reports the actual `CONNECT` method in `Request` and `RequestOutcome` for HTTP/2.

## Test

The tests start `NativeWebSocketExample.application()` with `TestServer` on an available loopback port.
The fixture owns application shutdown. Use `openWebSocket(...)` to send fragments, read complete replies
and check close codes. The tests use it to verify repeated demand, fragmented binary echo, the 64-byte
limit and the `400` and `403` handshake responses. One test uses the JDK client's `getSubprotocol()`
to check that the server selected `chat.v2` from the offered values.

These tests exercise HTTP/1.1 upgrades. HTTP/2 negotiation requires a client that supports extended `CONNECT`.
