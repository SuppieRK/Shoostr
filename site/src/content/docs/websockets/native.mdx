## Description

Native WebSocket handling exposes Jetty's listener and explicit message-demand APIs. Demand controls when the transport may deliver further events; it is a transport interaction rather than an application's work queue.

This task creates a fresh listener for each accepted HTTP upgrade and copies any required admission data before live request access ends. `HttpHeaders` supplies protocol names. `BadRequestException` rejects invalid upgrades with `400`, and `ForbiddenException` rejects forbidden upgrades with `403`, before connection handling starts.

Choose the native `routes.websocket(...)` overload for Jetty `Session.Listener`, explicit demand, subprotocol selection or connection limits. Its factory runs during HTTP admission and creates a listener for each accepted connection. Copy the needed path or identity there; do not retain the live handshake request or upgrade response. Use [managed callbacks](../managed/) for ordinary complete messages with sequential application callbacks.

Native callbacks retain [Jetty's execution contract](https://jetty.org/docs/jetty/12.1/programming-guide/client/websocket.html), so follow its callback and demand rules when sending asynchronously.
A `Session.Listener` must demand the next event explicitly, and a binary receive callback controls the lifetime of its borrowed buffer.
The [Jetty WebSocket architecture](https://jetty.org/docs/jetty/12.1/programming-guide/client/websocket.html) explains both contracts in more detail.

## Example

The `/native/{room}` route first requires exactly one trusted Origin, then requires an offered `chat.v2` subprotocol and selects it before returning the listener.
Its listener prefixes text with the detached room name, echoes binary bytes, and requests another event only after the preceding write completes.
Binary input is copied before its receive callback is completed, keeping the outgoing bytes valid after Jetty can reuse the receive buffer.
A failed write disconnects the session rather than leaving the listener waiting indefinitely.

The listener sets incoming text and binary message limits to 64 bytes each (UTF-8 bytes for text) and permits at most two pending outgoing data frames when the session opens.
These limits do not provide an application producer queue; if external producers send concurrently, bound their pending work and serialize native writes yourself.
Jetty owns the upgraded session and releases its transport resources when the connection or application closes.
The native factory performs its Origin check before returning the listener, following the same admission rule as [managed WebSockets](../managed/).
HTTP CORS and CSRF do not protect this handshake; authenticate private endpoints separately, because neither Origin nor a negotiated subprotocol establishes identity.

`http2()` also enables negotiated HTTP/2 extended CONNECT for registered WebSocket routes, while HTTP/1.1 GET upgrades remain available.
Only extended CONNECT with the `websocket` protocol enters that handshake path; ordinary CONNECT requests do not become WebSockets.
The routing key remains GET for both transports, but a selected HTTP/2 request reports CONNECT through the public request and outcome APIs.
