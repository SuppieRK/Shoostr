## Description

A WebSocket starts with an HTTP handshake, then carries messages in both directions over one connection.
Shoostr manages native frame demand and delivers complete messages to your callbacks. Use `WebSocketConnection`
to send messages or close an accepted connection. This example replies to text and binary messages and keeps
a separate counter for each connection.

- Register `routes.websocket(...)`. Text callbacks receive `String` values, and binary callbacks receive
owned `byte[]` values.
- The configuration callback runs once at registration time, before startup.
Make shared state safe for concurrent access.
- Callbacks for one connection run sequentially in the application's configured execution mode.
Different connections can run concurrently. See [application execution mode](../../lifecycle/executors/).
- Idle connections leave threads free for other work, and later callbacks can use a different thread.
Keep message state with the connection.

To convert messages through a codec, use [object messages](../objects/).

Use `beforeUpgrade(...)` to reject a handshake through ordinary HTTP exception handling. This example accepts
exactly one `Origin` value matching `https://app.example`. For any other result, it throws `ForbiddenException`
and Shoostr sends `403` before the connection opens.

:::note[Origin checks are not CORS]
- CORS governs which cross-origin HTTP responses browser scripts can read. Preflights and
`Access-Control-Allow-*` headers belong to that flow. For a WebSocket handshake, validate `Origin` on the server.
See [CORS](../../security/cors/) and the [WebSocket handshake](https://websockets.spec.whatwg.org/#opening-handshake).
- Shoostr skips HTTP CORS and HTTP CSRF for recognized WebSocket handshakes, including HTTP/2 extended CONNECT.
Check `Origin` explicitly in `beforeUpgrade(...)`. Configured authentication and native session handling still
apply before the connection opens.
- Origin checks help block connections from untrusted browser pages. A client outside the browser can supply
its own header value, so require a verified identity for private data.
See [authentication](../../security/authentication/)
and the [WebSocket origin security model](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.2).
:::

## Example

`/rooms/{room}` stores one text-message counter per connection in a concurrent map.

- Nonblank text increments the counter. The reply includes the room, the new count and the message.
- Binary messages are echoed. The counter stays the same.
- Blank text gets `error: message required`. The connection stays open and the counter stays the same.

Keep the HTTP request and response within the handshake's lifetime. `WebSocketConnection` can outlive the handshake.
It keeps the path, the path parameters and the initial `Principal` reference.

`send(...)` copies outgoing binary arrays and waits for the transport to finish the write. The peer can receive
the message later. A connection can close between an `isOpen()` check and a send.

- Catch recoverable message errors inside the callback so the connection can continue.
- An unexpected exception in an opening or message callback closes the connection with `1011` and a generic reason.
An `InterruptedException` uses `1001`. Use `onError(...)` to observe terminal failures.
- Close and error observers remove counters during normal operation. `afterClose(...)` clears the remaining entries
if shutdown prevents those observers from running.

Application shutdown cancels queued managed work and interrupts active callbacks. A borrowed native executor
keeps its original owner. Callbacks that ignore interruption can outlive application closure, so signal waiting
work before disposing of its resources. See [application shutdown](../../lifecycle/shutdown/).

For native demand, subprotocol selection, or message limits, use a [native WebSocket listener](../native/).

## Test

`TestServer` starts the application on an available loopback port. With `shoostr-test` you can
use `openWebSocket(...)` to connect through the fixture's client. The test fills the `room` segment in the path
callback and sets `Origin` in the handshake callback. Timed receives read complete messages in order, and the
fixture closes any outstanding test sockets.

The tests send fragmented text and binary messages, check independent counters and recovery after blank text,
and verify `403` handshake denial and `1000` normal closure. An extra route throws during message handling.
The next event must be a `1011` close with the generic reason `Processing failed`.

The fixture uses the JDK client to exercise the server's handshake checks. Browser cookie delivery and browser
handling of `Origin` require browser tests.
