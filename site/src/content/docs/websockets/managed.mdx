## Description

A WebSocket starts with an HTTP upgrade and then carries messages over a connection. Managed callbacks let application code handle complete messages without controlling native frame demand. `WebSocketConnection` is the handle used to send messages or close that accepted connection.

`ForbiddenException` rejects a disallowed handshake with `403` while it is still an HTTP exchange.

This task keeps per-connection state and responds to text and binary messages. The route's setup callback registers behavior before startup; connection callbacks run later as connections exchange messages. A rejected handshake can still return an HTTP error before the upgrade.

Register `routes.websocket(...)` to receive complete text as `String` and binary messages as owned `byte[]` values. Callbacks for one connection run sequentially under the [application execution mode](../../lifecycle/executors/); different connections can run concurrently. Idle state occupies no thread, and later callbacks may use a different one. Keep state per connection rather than in thread-local storage. Route configuration runs once at registration, so shared captures must be safe concurrently. This application uses a concurrent map of per-connection counters. For conversion through a codec, continue with [object messages](../objects/).

Use `beforeUpgrade(...)` to reject a handshake through ordinary HTTP exception handling before the connection opens.
This route requires exactly one `Origin` header matching `https://app.example`, rejecting missing or ambiguous values rather than treating them as trusted.

:::note[Origin checks are not CORS]
[CORS](../../security/cors/) controls which cross-origin HTTP responses browser scripts can read.
The [WebSocket handshake](https://websockets.spec.whatwg.org/#opening-handshake) does not use CORS preflights or browser enforcement of `Access-Control-Allow-*` headers, so validate `Origin` on the server before upgrading.

Shoostr skips HTTP CORS and HTTP CSRF for recognized WebSocket routes, including HTTP/2 extended CONNECT.
Use an explicit `beforeUpgrade(...)` Origin check for browser admission; inherited authentication and native session handling still run before upgrade.

Origin checking helps prevent connections initiated by untrusted browser pages, but it is not authentication: a non-browser client can supply that header.
Protect private data with a separately [verified identity](../../security/authentication/); see the [WebSocket origin security model](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.2) for the protocol distinction.
:::

## Example

The `/rooms/{room}` endpoint replies with the room, that connection's text-message count, and the message; binary messages are echoed without changing the counter.
Blank text receives `error: message required` without closing the connection or incrementing its counter.
`WebSocketConnection` contains detached path and identity data and can outlive the handshake, but the handshake request and response cannot.
`send(...)` waits for transport completion, not peer receipt, and copies outgoing binary arrays; an open-state check cannot guarantee that a later send will succeed.

Catch recoverable message errors inside the message callback so the connection can continue.
An uncaught callback failure closes the connection with `1011` and a safe reason; `onError(...)` observes terminal failure rather than recovering it or rendering an HTTP response.
Close and error observers remove counters during normal operation, and `afterClose(...)` clears any entries left when shutdown prevents those observers from running.
Application shutdown cancels queued managed work and interrupts active callbacks without closing a caller-supplied native executor.
Callbacks that ignore interruption can outlive application closure, so use the [lifecycle hooks](../../lifecycle/shutdown/) to signal waiting work before final resource disposal.
For native demand, subprotocol selection, or message limits, use a [native WebSocket listener](../native/).

## Test

`TestServer` is the HTTP test fixture: it starts the application on an available loopback port and owns its shutdown.

The tests exchange fragmented messages through the JDK WebSocket client, check independent counters and continued handling after invalid input, and verify handshake denial and close frames.
The failure fixture registers an extra route that throws, proving that private exception text does not reach the peer; these checks do not establish browser cookie delivery or Origin enforcement by a browser.
