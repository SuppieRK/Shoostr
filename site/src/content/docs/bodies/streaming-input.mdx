## Description

Streamed input lets a handler consume a request body incrementally instead of first collecting the whole body in memory. The input stream belongs to the active request and advances as it is read.

This task computes a checksum from arriving bytes and returns the result. Choose this approach when processing can happen chunk by chunk; use a buffered body when the handler needs one complete text or byte value.

Read `input()` as bytes arrive and update the checksum incrementally. Calling `input()` again returns the same stream at its current position. It does not rewind the body. Choosing streamed input excludes buffered reads and multipart parsing for that request.

The stream belongs to the active handler and is closed during framework finalization, so finish reading within that lifetime rather than handing it to detached work.
The configured request-byte limit applies as bytes are consumed, including skipped bytes.
Opening a stream or stopping early does not validate the unread remainder of an unknown-length body.

For a fixed-size prefix, `input().readNBytes(n)` returns after `n` bytes arrive or the body ends.
Once it has those bytes, it does not wait for a later chunk.
During the handler lifetime, valid zero-length reads return `0` without waiting for content, including at EOF.

## Example

The endpoint calculates SHA-256 with a per-request digest and a bounded transfer buffer, then returns the checksum only after successful consumption.
It uses the default 1 MiB input limit; excessive declared length is rejected before the handler, while an unknown-length overflow produces `413` during reading.
See [buffered bodies](../buffered/) for the body-mode comparison and [server options](../../application/server-options/) for general limit configuration.
