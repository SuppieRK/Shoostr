## Description

An `Upload` represents a file part while its request is being handled. To use the file after that request finishes, persist its content to an application-selected path. The saved path then belongs to your application, while the upload wrapper remains request-scoped.

This task accepts a multipart file, saves it, and returns information about the saved content. `Options` and `MultipartOptions` configure input limits before the handler runs. The handler uses `BadRequestException` when the required file is absent.

While the handler is active, call the upload's `persistTo(Path)` with the destination you selected. Shoostr then leaves the saved content for your application to retain or delete. Keep that path after the request finishes; the `Upload` wrapper and its content streams still belong to the request and must not be retained.

Choose a directory controlled by your application and generate destination names there.
Do not resolve a client-supplied filename against that directory; it is untrusted metadata and can contain path traversal text.
See [multipart fields and files](../multipart/) for part access, parser limits, and temporary-file behavior.

## Example

The endpoint requires a `document` upload, reserves a unique destination with `Files.createTempFile()`, and returns its generated filename with status `201` after persistence succeeds.
It removes only that reserved destination if persistence fails, leaving existing files untouched.
A later response failure does not discard successfully saved content.

The selected directory is created before startup and holds both temporary uploads and saved files.
This example retains the default multipart limits, including a 16,384-byte file-part memory threshold.
Persistence works for both in-memory and spilled uploads; it does not promise an atomic move across filesystems.

## Test

`TestServer` is the HTTP test fixture: it starts the application on an available loopback port and owns its shutdown.

The tests verify that both small and spilled uploads remain readable after the application closes.
They also check generated names, missing uploads, early directory validation, and preservation of existing files when a submitted filename contains traversal text.
Awaitility is an additional test library used to wait until cleanup leaves only the expected application-owned files.
