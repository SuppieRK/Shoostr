## Description

Keep an uploaded file after its request ends by saving it to a path your application chooses. In the handler, call
`persistTo(Path)` on the `Upload` with that destination.

Shoostr leaves the saved file for your application to retain or delete. Keep the returned `Path` for later work.
Use the `Upload` and its content streams only during the handler's lifetime.

Choose a directory your application controls and generate destination names there. Never use a client-supplied
filename to build the destination path. The name is untrusted metadata and can contain path traversal text.
See [multipart fields and files](../multipart/) for part access, parser limits, and temporary-file behavior.

## Example

The `/documents` handler saves one upload in this order.

1. Read the `document` file part. Throw `BadRequestException` if it is missing.
2. Reserve a unique destination with `Files.createTempFile()`.
3. Call `persistTo(...)` with that path. If it throws an `IOException` or a runtime exception, try to delete only
   the reserved destination and rethrow the failure.
4. Return the generated filename with status `201`.

Once persistence succeeds, the saved content remains available even if sending the response fails.

The example creates the storage directory before startup and uses it for both temporary uploads and saved files.
It keeps the default multipart limits, including the 16,384-byte memory threshold for file parts. The
[multipart example](../multipart/) lowers the threshold to 128 bytes to demonstrate spilling with small files.

`persistTo(...)` works for uploads held in memory or spilled to disk. Treat transfers across filesystems as
potentially non-atomic.

## Test

The HTTP tests create the app with `PersistUploadExample.application(directory)`. `TestServer` starts it on an
available loopback port and shuts it down when the fixture closes.

The tests read back a 4-byte upload and a 20,000-byte upload after the application closes. Two uploads with the
same submitted filename containing path traversal text receive distinct generated names, and an existing file
keeps its contents. The tests use Awaitility, an additional test library, to wait until cleanup leaves only the
expected files.

A missing upload returns `400` and creates no destination. Before startup, the example creates a missing storage
directory and rejects a regular file or `null` as the destination directory.
