## Description

Read text fields and uploaded files from the same multipart request. Shoostr exposes each file part as an `Upload`
that belongs to the current request.

This example reads fields and files inside the handler. `MultipartOptions` sets parsing limits and temporary
storage. Your application chooses where to save accepted files.

Create a `MultipartOptions` object, configure it, and pass it to `Options.setMultipart(...)` before constructing
`Shoostr`. The per-file limit cannot exceed the aggregate limit. Lower the per-file limit first if the new
aggregate limit would fall below it. Raise the aggregate limit first if the new per-file limit would exceed it.
An invalid setter call leaves the previous value in place. Passing `null` restores a property's default if it
fits the other limits.

`Shoostr` copies the settings during construction. Keep them fixed while it makes that copy. Later changes apply
only to future applications.

| To read | Use |
| --- | --- |
| The first text value under a name | `formParam(name)` |
| The first upload under a name | `file(name)` |
| Every upload under one name, in arrival order | `files(name)` |
| All uploads, grouped by name | `files()` |

An empty filename still identifies a file part. The file accessors return empty results for a non-multipart request.
See [request parameters](../../request/parameters/) for query and URL-encoded form input.

Shoostr parses the entire multipart body and validates each part's required metadata before exposing fields or
uploads. Switching between multipart parsing and [buffered or streamed input](../buffered/) throws
`IllegalStateException`.

Text fields accept an absent `Content-Type` or `text/plain`. Use UTF-8 if you declare a charset. Shoostr decodes
text as UTF-8 and preserves literal `+` characters.

| Problem | Response status |
| --- | --- |
| Unsupported text field media type or charset | `415` |
| Malformed multipart input | `400` |
| Configured size or part-count limit exceeded | `413` |

An upload and its content streams are available only during the handler.
Read them there, or [save the upload](../persist-upload/) before handing its content to later work.
Shoostr removes unretained temporary files when the exchange completes,
which can occur after the client receives its response.
During the handler lifetime, valid zero-length content reads return `0`, including at EOF.

## Example

The endpoint reads a title and summarizes the `document` uploads, including their exact bytes as hexadecimal text.
The per-part limit bounds each binary read. To checksum a raw request body without buffering it, use
[streamed input](../streaming-input/).

Treat submitted filenames as metadata. Choose a filesystem path in application code when saving a file.

The example sets the following parsing limits.

| Limit | Value |
| --- | --- |
| Complete multipart body | 8,192 bytes |
| Each file or text part | 1,024 bytes |
| Number of parts | 8 |
| Headers per part | 1,024 bytes |

The aggregate limit includes multipart boundaries and headers. Multipart parsing counts parts with `maxParts`.
Queries and URL-encoded forms use `maxParameters`. Multipart's aggregate limit is separate from `maxRequestBytes`.

The application creates the temporary directory before startup. A file part larger than 128 bytes spills to that
directory. This threshold selects storage for each file part. The parser uses the limits in the table to decide
whether to reject the request.

## Test

The HTTP tests create the app with `MultipartExample.application(directory)`. `TestServer` starts it on an available
loopback port and shuts it down when the fixture closes.

The tests send real multipart bodies with text fields, repeated files, binary content, and an empty filename. They
exercise all four parsing limits, check `400` for malformed part metadata and `415` for unsupported text field
representations, and verify that multipart parsing blocks buffered and streamed reads.

The spill test counts temporary files inside the handler. A 128-byte file creates none and a 129-byte file creates
one. The test uses Awaitility, an additional test library, to wait for temporary files to disappear after the
response. A separate test checks that application construction rejects a file path or `null` as the storage directory.
