## Description

A multipart request carries separately named parts, usually form fields and uploaded files. Shoostr exposes text fields through form accessors and file parts as `Upload` values. Each upload belongs to the current request until its content is explicitly persisted.

This task inspects submitted fields and files inside the handler. `MultipartOptions` configures parsing limits as part of the application's `Options`; it does not decide where your application keeps accepted files.

Read a text field with `formParam()` and its first named upload with `file()`. Choose `files(name)` for every upload under one name, or `files()` for the complete grouped collection. A submitted empty filename still represents a file part. When the request is not multipart, file accessors return empty results. Query and URL-encoded input use the separate [parameter accessors](../../request/parameters/).

Multipart parsing reads and validates the complete body before exposing fields or uploads.
It cannot be combined with [buffered or streamed input](../buffered/).
Text fields accept an absent content type or `text/plain`, with UTF-8 decoding; unsupported media types or charsets produce `415`, and malformed multipart input produces `400`.
Unlike URL-encoded forms, multipart fields preserve literal `+` characters.

An upload and its content streams are available only during the handler.
Read them there, or [save the upload](../persist-upload/) before handing its content to later work.
Shoostr removes unretained temporary files when the exchange completes, which can occur after the client receives its response.
During the handler lifetime, valid zero-length content reads return `0`, including at EOF.

## Example

The endpoint reads a title and summarizes the `document` uploads, including their exact bytes as hexadecimal text.
Its per-part limit makes this small binary read bounded; for a raw-body checksum without whole-body buffering, use [streamed input](../streaming-input/).
Submitted filenames are metadata, not trusted filesystem paths.

The configured limits are 8,192 bytes for the complete multipart body, 1,024 bytes per part, eight parts, and 1,024 header bytes per part.
Limit overflow produces `413`.
The per-part byte limit also applies to text fields, and the aggregate limit includes multipart boundaries and headers.
Multipart uses `maxParts`, not the query and URL-encoded `maxParameters` limit; its aggregate limit is separate from `maxRequestBytes`.

The application creates the selected temporary directory before startup.
A file part larger than 128 bytes spills to that directory; the threshold selects storage rather than rejecting the upload or limiting total request memory.
