## Description

Let clients reuse a file they already have or resume an interrupted download. Serve the application-selected file
with `response.file(...)`. Shoostr supplies file validators, evaluates conditional headers and can serve one byte
range at a time. The client manages its stored copies.

For the `GET` endpoint below, Shoostr checks preconditions before it considers a range. A failed precondition
prevents a partial response.
`If-Match` takes precedence over `If-Unmodified-Since`, and `If-None-Match` takes precedence over `If-Modified-Since`.

| Request condition                                                  | Response                                          |
|--------------------------------------------------------------------|---------------------------------------------------|
| Matching `If-None-Match`, or an eligible unchanged date            | `304` without a body                              |
| An eligible `If-Match` or `If-Unmodified-Since` precondition fails | `412` without a body                              |
| One satisfiable byte range                                         | `206` with `Content-Range` and the selected bytes |
| A valid but unsatisfiable range                                    | `416` with `Content-Range: bytes */length`        |
| Unsupported, multiple or malformed ranges                          | The full `200` representation                     |

Shoostr considers `Range` only for `GET` requests whose response would otherwise have status `200`.

A [strong ETag](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.1) identifies an exact revision and must
change whenever the file's bytes change. When a request includes `If-Range`, Shoostr honors the range only if the
header matches the file's current strong ETag. A weak tag, mismatched tag or date in `If-Range` results in the
full file.

Keep the selected file available and stable until the transfer completes. See [file downloads](../downloads/).

## Example

The example serves one fixed file revision. It sets the strong ETag `"revision-1"` before selecting the file
so a client can send that tag in `If-Range`.

Use that literal only for the fixed revision in this example. For a changing file, supply a strong tag tied
to the revision or let Shoostr generate the validators.
