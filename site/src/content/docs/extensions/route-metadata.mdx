## Description

Create an extension when reusable behavior needs its own configuration or lifecycle. To run a few callbacks
at named request phases, register [request hooks](../../lifecycle/hooks/) directly.

An extension implements one or both interfaces. Use the same settings type `C` when implementing both.

- `ApplicationExtension<C>` supplies application defaults.
- `RouteExtension<C>` supports selection on routes and groups.

Both interfaces share the ownership, setup, startup and shutdown methods of the sealed `Extension` interface.
Route and group configuration callbacks receive `Lifecycle`, which selects extensions, registers local request
hooks and collects route metadata. Inside `install(...)`, use `ApplicationCallbacks` to register application-wide
behavior.

This example builds a route catalog from descriptions collected during registration. The extension compiles them
into a fixed snapshot before the application starts serving requests.

### Select one provider instance

Pass the intended instance into reusable route-registration methods. Shoostr looks up selections by object identity,
so separate instances of the same class have separate settings and contributions.

- In a route or group callback, select it with `lifecycle.withExtension(instance)`. The first selection claims
  ownership and calls `install(...)` once. The call also enables the contribution and returns the scope's typed
  settings. Selecting the instance again in that scope returns the same settings without adding another contribution.
- For an `ApplicationExtension`, use `app.withExtension(instance)` before registering routes. Use
  `app.withExtension(instance, settings -> ...)` to customize the defaults. Registered endpoints inherit the
  selection. Shoostr rejects a second application-level selection of the same instance.
- Use `lifecycle.withoutExtension(instance)` to exclude its scoped contribution. Installation callbacks and owned
  resources remain with the application. A deeper `withExtension(instance)` includes the same provider again
  with its retained settings.

### Follow the provider lifetime

Shoostr calls the extension methods at these points.

| Method                               | Purpose and timing                                                                                                                                                                                                             |
|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `claimOwnership()` | Accept ownership before installation. Override this method to reject reuse of application-specific state or resources. A successful claim makes the application responsible for cleanup even if later setup fails. |
| `install(callbacks)`                 | Set up shared infrastructure at first selection. Callbacks registered here can see unselected requests. Put selected behavior in `configure(...)`. The collector freezes when this method returns. |
| `configure(endpoint, inherited)`     | Create the extension's own typed settings and register behavior for a selected route or group. Shoostr also calls it when a child inherits the selection.                                                                      |
| `beforeStart()`    | Finalize collected route facts and prepare owned resources after route metadata arrives, before the listener accepts traffic.                                                                                                  |
| `beforeStop()`     | Promptly signal owned work to finish before native graceful shutdown, including cleanup after incomplete installation or startup. Final disposal belongs in `close()`.                                                         |
| `close()`                            | Release owned resources after a successful ownership claim, including when installation or startup fails. Do not close borrowed dependencies.                                                                                  |

### Configure inherited settings

Both interfaces require `configure(...)`. Use it to register behavior on the supplied scope and return its
settings. The catalog returns a `Description`, so `lifecycle.withExtension(catalog).summary(...)` sets the
description for that scope.

- Read the parent settings from `inherited`. The argument is `null` when there are no inherited settings.
- Give each scope its own mutable settings. Shoostr calls `configure(...)` for inherited selections without
  replaying the group callback. Independent settings let each child change its own values. A provider with no
  scope-local settings can return itself.
- Register the extension's contributions on the supplied `Lifecycle`. Select collaborating extensions separately
  in the application's route or group configuration callback.

Authentication, CSRF and CORS keep the selected owner through inheritance and exclusion. Re-inclusion uses the
same instance. CORS lets a child replace the complete inherited policy with
`lifecycle.withExtension(cors).policy(replacement)`. Parent and sibling settings keep their own policies. See [CORS](../../security/cors/).

HTTP sessions use Jetty configuration at application level and the ordinary request API. See [sessions](../../security/sessions/).

### Register callbacks and route metadata

Use the supplied `Lifecycle` in `configure(...)` to register request behavior for selected routes and groups.
Use `endpoint.onRoute(...)` to receive registration metadata before startup. The table shows which methods are
available on the application, the local scope, or both.

| Registration method                                 | What it provides                                                                                                                                                                                                 |
|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `onRequestHeaders(...)`    | Application-only hook before matched-route processing, including unmatched requests.                                                                                                                             |
| `onRouteMatched(...)`      | Application or local hook after a route matches, when its composed route pattern is available.                                                                                                                   |
| `beforeRouteHandler(...)`  | Application or local admission hook before the handler. Throw to reject the request; response streaming is unavailable in this phase.                                                                            |
| `afterRouteHandler(...)`   | Application or local hook after the handler returns successfully; skipped when it throws.                                                                                                                        |
| `beforeResponseFlush(...)` | Application or local read-only hook before each framework-owned response flush.                                                                                                                                  |
| `afterResponseFlush(...)`  | Application or local read-only hook after each committed framework-owned response flush.                                                                                                                         |
| `afterRequest(...)`               | Application or local terminal observer with a detached `RequestOutcome` after application finalization and transport termination.                                                                                |
| `observe(...)`                                      | Application or local request observation with context attachment and cleanup across executor handoffs. Application observations include unmatched requests; local observations begin only after a route matches. |
| `onRoute(...)`                    | Local registration metadata for HTTP and SSE routes: method, composed path template and conditional availability. Runs before `beforeStart()` without invoking handlers or evaluating conditions.                |
| `status(...)`                                       | Local renderer for a framework-generated status. A matching local renderer takes precedence over the application renderer.                                                                                       |

The [request lifecycle reference](../../lifecycle/hooks/) explains callback order and completion rules,
while [endpoint executors](../../lifecycle/executors/) explains observation context across thread handoffs.

## Example

`RouteCatalogExample.application(BooleanSupplier previewAvailable)` selects the catalog as an application default
before registering routes. `RouteCatalog` copies the description for each scope and receives the method, composed
path template and conditional flag through `onRoute(...)`. Its `beforeStart()` compiles a text snapshot. Requests
to `/catalog` read that snapshot directly.

| Route | Catalog behavior |
| --- | --- |
| `/catalog` | Inherits the application-default description. |
| `/health` | Excludes both its catalog entry and the discovery header. |
| `/api/status` | Overrides its own description. `/api/items/{id}` keeps the description inherited from `/api`. |
| `/preview` | Appears with a conditional flag even while unavailable. |

`onRoute(...)` reports ordinary HTTP and SSE bindings. WebSocket handshakes and static mounts are outside that
coverage. The flag records the presence of a condition, and the application checks that condition on matching
requests. Restrict access if route names reveal private application structure. See [authentication](../../security/authentication/).

The catalog atomically rejects a second owner and keeps only detached registration facts. When the owning application
closes, the catalog clears its state. A successful claim transfers cleanup responsibility even if later setup fails.
The original owner remains responsible for a provider the application has yet to claim or whose claim was rejected.

For extensions that own long-lived work, use `beforeStop()` to signal work promptly and `close()` for final disposal.
Shoostr invokes each phase in reverse claim order. Borrowed registries, SDKs and clients stay with their owners.

## Test

`TestServer` starts the application from `RouteCatalogExample.application(...)` on an available loopback port
and owns its shutdown. The tests also configure a catalog directly to exercise ownership and snapshot behavior.

- The catalog response contains composed route templates and each route's inherited or overridden description.
  `/health` appears neither in the catalog nor with the discovery header.
- A second application fails to claim the catalog. The first application still serves its route and keeps its
  catalog until shutdown. Closure clears the catalog state.
- Requests to `/preview` check availability, while startup and catalog requests leave the condition unevaluated.
- The example rejects blank descriptions. Changing a retained description after startup leaves the snapshot intact.
