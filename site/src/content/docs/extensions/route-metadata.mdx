## Description

An extension adds reusable behavior to an application, such as collecting route descriptions or tracing requests.
It can provide its own settings for routes and groups, register request hooks, and manage resources throughout the application lifecycle.

Use an extension when that behavior needs its own configuration or lifecycle.
For a few request callbacks, register [request hooks](../../lifecycle/hooks/) directly.

`Extension<C>` defines reusable behavior and its typed settings.
Route and group configuration callbacks receive an `Extensions` object, which selects installed extensions and exposes `extensions.lifecycle()` for local request hooks and status renderers.
You can register those local callbacks without implementing or installing an extension.

Implement `Extension<C>`, create one extension instance, and pass it to `app.extensions(instance)` before registering routes.
Reuse that same instance in every `extensions.with(instance)` call.
Shoostr selects extensions by object identity: another instance of the same class does not refer to the installed extension.
In the example, `catalog` is the instance shared by `.extensions(catalog)` and `extensions.with(catalog)`.

Calling `app.extensions(instance)` immediately invokes that instance's `install(...)` method, where it can register application-wide behavior.
Selecting it with `extensions.with(instance)` includes its behavior and returns the current scope's typed settings.
Use `app.configureExtensionsDefaults(...)` once, before registering routes or groups, to select defaults across the application without a root group.
A route or group inherits those defaults and can use `extensions.without(instance)` to exclude that instance's scoped behavior.
A deeper `with(instance)` includes it again with the retained settings; repeated selection does not duplicate its contributions.
Exclusion does not undo installation callbacks or release resources owned by the application.

Each extension method has a specific role:

| Method | Purpose and timing |
| --- | --- |
| <code>claim<wbr />Ownership()</code> | Accept ownership before installation. Override it to reject reuse when the extension owns application-specific state or resources; a successful claim makes the application responsible for cleanup even if later setup fails. |
| `install(callbacks)` | Register application-wide request hooks and observations as soon as the instance is installed. The supplied registration object stops accepting callbacks when this method finishes. |
| `configure(endpoint, inherited)` | Create the extension's own typed settings and register behavior for a selected route or group. Shoostr also calls it when a child inherits the selection. |
| <code>before<wbr />Start()</code> | Finalize collected route facts and prepare owned resources after route metadata arrives, before the listener accepts traffic. |
| <code>before<wbr />Stop()</code> | Promptly signal owned work to finish before native graceful shutdown, including cleanup after incomplete installation or startup. Final disposal belongs in `close()`. |
| `close()` | Release owned resources after a successful ownership claim, including when installation or startup fails. Do not close borrowed dependencies. |

Implement `configure(...)` to contribute behavior for selected routes and groups and, when needed, expose their settings.
Its return type `C` defines those settings: the catalog returns a `Description`, and `extensions.with(catalog).summary(...)` changes that scope's description.
An extension that only contributes application-wide behavior can leave `configure(...)` unimplemented.

The `inherited` argument contains the parent scope's settings, or null for the first selection.
Return independent mutable settings rather than mutate the parent; a provider without scope-local settings may return itself, while registering its behavior on the supplied collector.
Shoostr calls it again for inherited selections without replaying the user's group callback, allowing child routes to change the settings defined by that extension without affecting siblings.
Authentication, CSRF and [CORS](../../security/cors/) retain their selected owner through inheritance, including after exclusion: a child cannot substitute a different instance.
CORS provides local policy settings: `extensions.with(cors).policy(replacement)` replaces the complete inherited policy without changing its owner or a sibling's settings.
[Sessions](../../security/sessions/) use application-level native Jetty configuration and ordinary request methods rather than scoped extension selection.
Register contributions on the supplied scope; select collaborating extensions separately in the user's route or group callback, not through nested `with(...)` calls inside the provider.

Inside `install(...)`, `ApplicationCallbacks` registers behavior across the application, including routes that do not select the extension.
Inside `configure(...)`, use `endpoint.lifecycle()` for request behavior on selected routes and groups.
Cold route metadata remains on `endpoint.onRoute(...)`; it is separate from the request lifecycle.
The registration methods below belong to the lifecycle collector unless marked as application-only, metadata or installation checks:

| Registration method | What it provides |
| --- | --- |
| <code>on<wbr />Request<wbr />Headers(...)</code> | Application-only hook before matched-route processing, including unmatched requests. |
| <code>on<wbr />Route<wbr />Matched(...)</code> | Application or local hook after a route matches, when its composed route pattern is available. |
| <code>before<wbr />Route<wbr />Handler(...)</code> | Application or local admission hook before the handler. Throw to reject the request; response streaming is unavailable in this phase. |
| <code>after<wbr />Route<wbr />Handler(...)</code> | Application or local hook after the handler returns successfully; skipped when it throws. |
| <code>before<wbr />Response<wbr />Flush(...)</code> | Application or local read-only hook before each framework-owned response flush. |
| <code>after<wbr />Response<wbr />Flush(...)</code> | Application or local read-only hook after each committed framework-owned response flush. |
| <code>after<wbr />Request(...)</code> | Application or local terminal observer with a detached `RequestOutcome` after application finalization and transport termination. |
| `observe(...)` | Application or local request observation with context attachment and cleanup across executor handoffs. Application observations include unmatched requests; local observations begin only after a route matches. |
| <code>on<wbr />Route(...)</code> | Local registration metadata for HTTP and SSE routes: method, composed path template and conditional availability. Runs before `beforeStart()` without invoking handlers or evaluating conditions. |
| `status(...)` | Local renderer for a framework-generated status. A matching local renderer takes precedence over the application renderer. |
| <code>require<wbr />Installed(...)</code> | Check that another exact extension instance is installed in this application, without selecting its configuration or adding request behavior. |

The [request lifecycle reference](../../lifecycle/hooks/) explains callback order and completion rules, while [endpoint executors](../../lifecycle/executors/) explains observation context across thread handoffs.

## Example

`RouteCatalog` copies a short description for each selected scope and receives the final composed method, path template and conditional-availability flag through `onRoute(...)`.
Its `beforeStart()` compiles those facts into a fixed text snapshot, so serving `/catalog` neither executes documented handlers nor evaluates availability conditions.
Application defaults select the catalog before route registration; `/catalog` inherits their description, and `/health` explicitly excludes catalog facts while retaining the installation-wide discovery header.
The `/api/status` override leaves the inherited `/api/items/{id}` description unchanged.

Route facts cover ordinary HTTP and SSE bindings, not WebSocket handshakes or static mounts, and an availability flag describes a condition rather than its current result.
Keep the catalog public only when its route names are public; apply [authentication](../../security/authentication/) if disclosing those names would expose private application structure.

The catalog atomically rejects reuse by another application, keeps no live request objects, and clears its state when its owning application closes.
A successful ownership claim transfers cleanup responsibility even if later setup fails; rejected or not-yet-claimed providers remain with their existing owner.
For extensions that own long-lived work, `beforeStop()` is the prompt signalling phase and `close()` is final disposal, both in reverse claim order; never close borrowed registries, SDKs or clients on their owners' behalf.
