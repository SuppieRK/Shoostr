## Description

Use `response.negotiate(...)` for content negotiation: select a response media type from the request's `Accept` header, then generate the matching representation.
Selection respects the client's quality values and wildcards; when preferences are equal, the candidates retain server order.
A missing `Accept` header selects the first candidate, while an explicit empty list or an unsupported preference produces `406`.
Malformed syntax produces `400` instead.

Negotiation adds `Accept` to `Vary` without discarding existing fields, including when the result is `406`.
A malformed header fails before this addition.
For the underlying HTTP rules, see [Accept](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1) and [Vary](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5).

## Example

The `/greeting` endpoint offers JSON first and UTF-8 text second.
Both branches provide their own bytes: negotiation selects metadata, but does not serialize objects or change their encoding.
For object conversion, use an [explicit JSON codec](../codec/); the usual [finite response rules](../../responses/bodies/) still apply.
