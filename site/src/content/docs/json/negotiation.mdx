## Description

Use the request's `Accept` header to choose how to send the same result. In this example, the client can request
a greeting as JSON or plain text. Each representation combines body bytes with media metadata.

Pass the offered `MediaType` values to `response.negotiate(...)` in server preference order. Shoostr matches each
offer against the media types and wildcards in `Accept`. The most specific match sets the offer's quality value
(`q`). Your handler produces the body in the selected format.

| Request                                 | Result                                                               |
| --------------------------------------- | -------------------------------------------------------------------- |
| `Accept` allows one or more offers      | The highest-quality offer wins. Ties follow server preference order. |
| No `Accept` header                      | Shoostr selects the first offer.                                     |
| `Accept` is present with an empty value | `406 Not Acceptable`                                                 |
| `Accept` allows none of the offers      | `406 Not Acceptable`                                                 |
| `Accept` has malformed syntax           | `400 Bad Request`                                                    |

Shoostr adds `Accept` to `Vary` when needed so caches can take the client's preferences into account. It preserves
existing `Vary` entries, including on a `406` response. A malformed `Accept` header produces `400` before Shoostr
adds `Accept` to `Vary`.
For the underlying HTTP rules, see [Accept](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1)
and [Vary](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5).
