## Description

Switch a route on or off while the application is running. Register the route once, then use a live flag or a request
condition to control its availability. For credential and permission checks, see how to
[require authentication for routes and groups](../../security/authentication/).

Use `when(...)` to register routes under a condition. A `BooleanSupplier` reads an application flag. A
`Predicate<Request>` checks the current request.

Shoostr selects a route by method and path. After the request passes admission checks, including any required
authentication, Shoostr evaluates the selected route's conditions from the outer scope inward. On the first `false`,
it returns `404` with `Cache-Control: no-store` and skips any other matching route.

Method discovery uses the registered routes. An unavailable route can still contribute its method to the `Allow`
header in a generated `405` response.

## Test

The HTTP tests create the app with `ConditionalRoutesExample.application(...)`. `TestServer` starts it on an available
loopback port and shuts it down when the fixture closes.

The live-flag test gets `404`, `200`, and `404` from the same running app as it flips the flag on and off. With the flag
on, the route still requires `preview=true`. The catch-all test checks that `/preview/latest` returns `404` while
`/preview/other` still reaches the fallback. `PUT /preview/latest` gets `405` with `GET` and `POST` in `Allow` even
when the conditional routes are unavailable. A separate test checks that the example factory rejects a null flag.

The test for evaluation order sends `preview=%FF`. With the flag off, the request receives `404` before the inner
condition reads the query. With the flag on, the inner condition tries to decode the value and produces `400`.
