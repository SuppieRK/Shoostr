## Description

A route group gives related endpoints a shared path prefix and inherited behavior. A `Routes` value is a registration view for that scope, so the same registration method can be reused under different prefixes.

The configuration callback receives `Extensions`, Shoostr's built-in scope-configuration object. Its `lifecycle()` collector registers local request hooks. A before-handler hook runs after matching and any required authentication, before the endpoint handler; the example uses it to add a header. Child routes inherit that behavior.

This configuration object is separate from an installed `Extension<C>` provider, which is an optional integration with its own settings or lifecycle. Its type parameter `C` describes the settings the provider exposes. The grouping example creates no provider: it only configures the group's built-in request hooks.

Create a common prefix with `path(...)`, then pass a registration method when several groups share endpoint definitions. Prefixes are relative to their parent even if they start with `/`: combining `/api` and `/v1` registers `/api/v1`.

An empty prefix creates a pathless group: its configuration applies to its routes without adding a URL segment.
Within a group, `get(handler)` registers the group's own endpoint, while `get("/", handler)` registers the distinct trailing-slash endpoint.

## Example

The `notes(...)` method is reused under `/api/v1/notes` and `/api/v2/notes`.
Both groups inherit the API header, but only the second receives the version header; the pathless status group and public sibling remain outside that configuration.
The nested account route also reads parameters captured by both parent and child paths.

Group configuration runs before its registration callback, and the registration callbacks run before the application starts rather than for each request.
