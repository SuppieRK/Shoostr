## Description

An OpenAPI document describes an HTTP API's operations, parameters and representations. It is a description for readers and tools; it does not implement the API or enforce its validation and access rules.

This example uses `shoostr-openapi` and Jackson 3's `jackson-databind` library for its JSON request and response handling.

Shoostr's `OpenApi` provider collects explicit operation descriptions from registered routes. Register that provider with the application, then use the route's `Extensions` configuration object to select it and supply operation settings. Mounting the generated document is a separate route.

This task describes an item API, serves its document, and keeps another document independent. `MediaType` names representations, while the handler uses `BadRequestException` for invalid input independently of the schema.

Build explicit Swagger OpenAPI models, register the `OpenApi` instance from `shoostr-openapi`, and select it in the relevant route or group configuration. A group supplies independent operation defaults; an endpoint can replace its summary, identifier, parameters, representations and responses. Serve the generated JSON by separately registering `docs.handler()`. Installation does not expose a URL or infer a document by scanning classes, annotations or codecs.

Schemas describe the API rather than validate requests, choose a codec or enforce authentication.
Keep those responsibilities in the actual handlers and security configuration, even when an operation declares required fields or a security scheme.
Likewise, separate documents provide separate descriptions, not access-control boundaries.
The [OpenAPI 3.1.1 specification](https://spec.openapis.org/oas/v3.1.1.html) explains operations, reusable schemas and security descriptions in more detail.

Construct native `Schema` models for OpenAPI 3.1 rather than relying on annotation scanning or model inference.
Explicit path parameters must match the route template and be required. Constrained path parameters need an inline schema with exactly the string type; a referenced, content-based or non-string declaration is rejected. An existing pattern is intersected with the route constraint.
Published catch-all paths, unsupported HTTP methods, missing path declarations and duplicate operation identifiers fail startup.
Known local component references are checked against the document. External and other JSON Schema references are preserved without fetching them or claiming complete JSON Schema validation.

Operation defaults are independent. Summary, description and operation identifier replace inherited scalar values; tags accumulate without duplicates. A parameter replaces the same name/location, and a response replaces the same status, preserving unrelated entries. Request-body and security declarations replace their entire inherited values. See [OpenApiOperation](https://github.com/SuppieRK/Shoostr/blob/main/openapi/src/main/java/io/github/suppierk/shoostr/openapi/OpenApiOperation.java) for replacement and accumulation rules.
Generated JSON remains subject to the application's finite-response limit. Large schemas do not bypass that limit; UI assets use bounded streaming.

## Example

The item API defines a reusable schema, a constrained path parameter, and JSON request and response representations.
Its POST handler checks the input independently, including malformed JSON, missing or blank names, and trailing JSON values.
The operations endpoint selects another `OpenApi` instance, so it appears only in the separate operations document.

Generation runs before the listener starts and serves a fixed byte snapshot afterward, without executing documented handlers or evaluating availability conditions.
A conditional route remains described even when currently unavailable; use `hidden()` to exclude a selected binding instead of treating a runtime condition as documentation selection.
Keep operation identifiers unique within each document, and avoid conflicting method/path descriptions that the OpenAPI format cannot distinguish.
Protect specification URLs explicitly when they describe private operations; the [local UI recipe](../ui/) covers the page, assets and specification together.
