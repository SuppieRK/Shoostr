## Description

An OpenAPI UI is a browser page for exploring a generated API document. The page, its assets and the document are separate HTTP resources, so each needs its own route and access policy.

The `OpenApi` provider supplies the document and a prepared UI handler. A provider is a registered integration object; a route's `Extensions` configuration selects its scoped settings. The protected example also uses `Pac4j`, Shoostr's adapter for a configured pac4j authenticator. It verifies credentials before those private resources are returned. `MediaType` describes the representation sent by an HTTP response.

Register `OpenApi.uiHandler()` from `shoostr-openapi` to serve its prepared page and assets locally. Add the specification URL, page path ending in `/`, and catch-all asset route explicitly; installing the document adds none of them. The handler serves only four prepared resources and returns `404` for other asset paths. It needs no CDN or external specification validator.

Protect all three registrations when the API description is private, rather than protecting only the HTML page.
This example uses `shoostr-pac4j` with `pac4j-http` to apply the same Basic authentication policy to the page, assets and specification.
Its fixed credentials are for local demonstration only; use a real credential verifier and HTTPS for deployed Basic authentication, as described in the [pac4j recipe](../../security/pac4j/).

## Example

The API's `/me` operation requires authentication independently of its OpenAPI security description.
Use the UI's **Authorize** action to supply API credentials explicitly: API calls omit browser cookies and cached HTTP credentials, while the same-origin specification request can use the documentation login.
Authorization is not saved across page loads. This UI policy does not support API authentication that depends on browser session cookies; use another client for those operations.

Keep the UI base path and specification path literal and same-origin, and hide the UI group from the document if a parent group selects it.

## Test

`TestServer` is the HTTP test fixture: it starts the application on an available loopback port and owns its shutdown.

`Options` holds Shoostr's buffering limits. The bundle-size assertion compares the streamed asset with the default finite-response limit; serving the asset does not require raising that limit.

The tests check authentication on every resource and the actual API, inspect the published UI settings, and retrieve the bundled assets, including the large JavaScript bundle.
They verify the HTTP responses and bootstrap configuration, not execution of Swagger UI in a browser.
