## Description

Set an error response once for the application or a group of routes. In this example, a missing `name` gets
`400` at `/input` and `409` at `/group/input`, where the group has its own renderer. A renderer receives the
exchange's original `Request` and `Response` and can set the status, headers and body.

Throw an `HttpException` subtype such as `BadRequestException` when you know the HTTP status for a failure.
`HttpClientException` and `HttpServerException` carry `4xx` and `5xx` statuses, respectively. Other unhandled
exceptions produce `500`. The default body uses the status reason and keeps diagnostic exception text private.
The [HEAD and finite-response limits](../../responses/bodies/) still apply.

To customize the error response, register a renderer with `app.exception(...)` for the application or
`routes.exception(...)` for a route scope and its descendants.

- A matching renderer from the route scope takes precedence over an application-wide renderer.
- Among the scope's own and inherited mappings, the most specific matching exception class wins.
- A child replaces an inherited mapping for the same class. An inherited mapping for a more specific class
  still wins over a broader mapping in the child.
- Shoostr matches the directly thrown exception and ignores its cause chain.

Finish registration before startup. Shoostr rejects a second application-wide renderer for the same exception class.
Registering the same class again in a route scope replaces that scope's mapping.

A scope mapping covers every endpoint in the scope, including endpoints registered earlier in a fluent chain.

## Example

When `/checkout` fails, Shoostr discards its staged body and private header before the application renderer
writes the error response. The `/number` handler lets `NumberFormatException` reach its specific renderer.
The `/recover` handler catches that exception itself. The built-in and unhandled routes show the default
error responses.

Sending the status and headers commits the response. From that point, the status, headers and any body bytes
already sent are final.

| When the exception escapes                                  | What Shoostr does                                                                                                                       |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| The handler throws before commitment and a renderer matches | Clears staged application output and sets the initial error status before calling the renderer. Framework-required metadata can remain. |
| The renderer throws before commitment                       | Sends the safe `500` fallback and skips any other renderer.                                                                             |
| The handler or renderer throws after commitment             | Aborts the response.                                                                                                                    |

The [streaming recipe](../../streaming/output/) covers buffering, source cleanup and the handler-owned writer
lifetime. Use [status renderers](../statuses/) for generated `404` and `405` responses. Use
[Problem Details JSON](../problem-details/) for structured errors.
