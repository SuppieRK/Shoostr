## Description

Headers carry metadata about an HTTP request. Cookies are client-supplied values carried in its Cookie header, commonly used to return state established by a previous response. Neither value is trusted identity by itself.

The handler's `Request` provides accessors for one value, repeated values or the full collection. This task reads both forms and makes their naming and repetition rules visible in the response.

Choose `cookie(...)` or `header(...)` for a first value, `cookies(...)` or `headers(...)` for repeated values, and `cookieMap()` or `headerMap()` for the full collection. Header lookup is case-insensitive, including map access. Cookie names remain case-sensitive, so `theme` and `Theme` are distinct.

Repeated header fields retain their order without splitting comma-separated content.
Cookie values are not URL-decoded, so `a+b%2F` remains unchanged.
Duplicate cookie names remain visible; reject ambiguous duplicates when a value affects security rather than silently trusting the first one.

## Example

The preferences endpoint shows all three accessor forms for `X-Label` and the nonsecurity `theme` preference.
It only reads incoming cookies; [setting and deleting response cookies](../../responses/cookies/) is a separate operation.

Header collections capture construction-time fields after native customization, and cookie parsing follows the configured transport policy.
The default cookie policy can discard malformed fragments or unquote values, so do not rely on every malformed cookie being rejected.
Retain a [snapshot](../state/) rather than the live request when values are needed after handling ends.
