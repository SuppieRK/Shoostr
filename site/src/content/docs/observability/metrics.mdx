## Description

Measure HTTP requests in the `MeterRegistry` your application owns and configures. Shoostr's `MicrometerMetrics`
extension observes each selected request through terminal completion. This example measures an API group and leaves
its health endpoint outside the selection.

Install the extension and select where it runs.

1. Pass your `MeterRegistry` to `new MicrometerMetrics(registry)` from `shoostr-micrometer`.
2. In a route or group configuration callback, call `lifecycle.withExtension(metrics)` on the supplied `Lifecycle`.
   Shoostr sets up the shared extension automatically.
3. For application-wide defaults, call `app.withExtension(metrics)` before registering routes. Use
   `lifecycle.withoutExtension(metrics)` for local exclusions.

The extension registers an observation on each selected endpoint. A request must match a selected endpoint to be measured.

| Meter | Type | What it measures |
| --- | --- | --- |
| `http.server.requests` | Timer | The count and duration of completed requests, with `method`, `route`, `status` and `error` tags. |
| `http.server.requests.active` | Long-task timer | Requests still active from observation start through application cleanup and transport completion. |

The completed timer uses these tag values.

- `method` uses the recognized HTTP method name or `OTHER` for an unknown method.
- `route` uses the composed route template, such as `/api/items/{id}`. Requests for different item IDs share a timer when their other tags match.
- `status` uses the final committed status code. `0` means Shoostr committed no final response.
- `error` uses `transport` for a transport failure, `application` for an application failure, `server` for a 5xx status with no recorded failure, or `none` otherwise. Transport failures take precedence. The tag excludes exception text.

Micrometer documents the statistics each meter can report, depending on the backend.
[Timer reference](https://docs.micrometer.io/micrometer/reference/concepts/timers.html) ·
[Long-task timer reference](https://docs.micrometer.io/micrometer/reference/concepts/long-task-timers.html)

Use the [Maven and Gradle installation guide](../../start/libraries/) for the published integration coordinates.

## Example

The example selects metrics on `/api`, so requests to `/api/items/{id}` are measured. `/health` sits outside that group and stays unmeasured.

Your application manages the registry.

- Configure its filters, exporters and export destinations.
- Keep the borrowed registry open until Shoostr and any caller-owned tasks that use it have finished. Close the registry yourself.
- Keep user identifiers and credentials out of metric tags.

## Test

The tests start `RequestMetricsExample.application(registry)` with `TestServer`, which opens a loopback port and
owns application shutdown. They collect detached `RequestOutcome` summaries through `afterRequest(...)` and wait
for them before checking the meters for a completed request.

The tests inspect Micrometer's `SimpleMeterRegistry` in process.

- Requests for items `41` and `42` increment the same timer. A request to `/health` creates no completed timer.
- A paused request holds one active sample. At completion, the active count returns to zero and the completed timer records one request.
- A thrown failure records `status=500` and `error=application` and keeps the exception message out of the meter IDs.
- The registry records a measurement on the application's `application.work` timer while the server is running.

Backend ingestion is outside these checks.
