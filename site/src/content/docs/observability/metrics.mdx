## Description

Request metrics summarize activity across many exchanges. Micrometer stores those measurements in a `MeterRegistry`, which remains owned and configured by your application. Shoostr's `MicrometerMetrics` adapter connects request processing to that registry. It is an installed provider, an integration object registered with the application, and it also creates per-request observations.

An observation follows one request until it terminates. The built-in `Extensions` scope-configuration object exposes `lifecycle().observe(...)` to attach observations to a route or group. This task measures a selected API group while leaving a health endpoint outside that selection.

Supply an application-owned `MeterRegistry` to `MicrometerMetrics` from `shoostr-micrometer` and register the adapter. Select observation on the intended routes or groups with `extensions.lifecycle().observe(metrics)`. The metrics adapter creates observations rather than typed route settings, so select it through `observe(...)`, not `extensions.with(metrics)`.

The `http.server.requests` timer records completed count and duration with `method`, `route`, `status` and `error` tags.
It uses composed route templates instead of raw identifier paths, normalizes unknown methods to `OTHER`, and distinguishes `transport`, `application`, `server` and `none` error categories without recording exception text.
The `http.server.requests.active` long-task timer tracks admitted observations that have not yet terminated, rather than counting only time inside the handler.
Micrometer's [timer](https://docs.micrometer.io/micrometer/reference/concepts/timers.html) and [long-task timer](https://docs.micrometer.io/micrometer/reference/concepts/long-task-timers.html) references explain these different measurements and their backend-dependent statistics.

## Example

The `/api` group measures its item requests, while `/health` remains unselected.
For application-wide observation, including unmatched requests and early failures, configure `allRequests()` on the adapter before installing it instead of adding the local observation shown here.
App-wide unmatched requests use `UNMATCHED` as the route tag, and a terminal status of zero indicates that no final response was committed.

The application controls registry filters, exporters and export destinations; Shoostr borrows the registry and does not close it.
Keep metric tags free of user identifiers or credentials, and retain the registry until any outstanding caller-owned tasks have finished.

## Test

`TestServer` is the HTTP test fixture: it starts the application on an available loopback port and owns its shutdown.

`afterRequest(...)` registers a terminal callback receiving `RequestOutcome`, a detached completion summary. The test collects those summaries to wait for request termination before checking its meters.

The tests use Micrometer's `SimpleMeterRegistry` to check template-based counts, selective observation, active-request transitions and a bounded application-failure label.
They also record a new application metric after Shoostr closes to verify registry ownership.
These are in-process instrumentation checks, not proof of ingestion by a monitoring backend.
