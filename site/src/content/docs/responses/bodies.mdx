## Description

Choose how to send the response body. Use `text(value)` for UTF-8, `text(value, charset)` for a different encoding,
or `body(...)` for bytes your application already encoded. Set the status with `status(...)`, for example
`status(HttpStatusCodes.CREATED.value())` for `201`.

The text helpers set `Content-Type` with the charset they use to encode the body. Encoding follows
`String.getBytes(Charset)`, which substitutes replacement bytes for malformed or unmappable input. For Java objects,
use an [explicit JSON codec](../../json/codec/).

For encoded bytes, pass a `MediaType` that describes the body. `MediaType.of(...)` normalizes a bare `type/subtype`
and rejects parameters, ranges, wildcards, and surrounding whitespace. `withCharset(...)` labels the bytes with a
charset. Encode the bytes in that charset before passing them to `body(...)`. Use the `String` content-type overload
for arbitrary parameters. `body(...)` copies the byte array, so later changes to the array leave the response intact.

[Register the `HEAD` route explicitly](../../routing/methods/). Shoostr sends representation metadata and suppresses
the body bytes.

Leave the body unset for `204`, `205`, and `304`. For requests other than `HEAD`, Shoostr rejects a staged nonempty
body at completion and returns `500` under default error handling.
Use [`304 Not Modified`](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5) for a conditional `GET` or `HEAD`
when the client can reuse its existing representation.

## Example

The messages endpoint returns `201` with UTF-8 text, while `/bytes` sends binary data and `/latin1`
uses the text helper to select ISO-8859-1.
The DELETE handler returns `204`; the matching `GET` and `HEAD` handlers for `/message` select the same representation,
with HEAD suppressing the transmitted bytes.

This example caps finite response bodies at 64 bytes with `maxResponseBytes`. If the byte array exceeds that limit,
`body(...)` throws `IllegalArgumentException` before replacing any staged output.

Finite output stays staged until the handler returns successfully. Selecting another body replaces the previous
one. Once the response commits, its status, headers, and any bytes already sent cannot be replaced.
See [exception recovery](../../errors/exceptions/) for what Shoostr can send if an error occurs.

Use `Response` on its owning thread and within the request-handling lifetime. Shoostr owns completion and closure.

For file output and its longer transfer lifetime, use the [download recipe](../../resources/downloads/).
For incremental output while the handler runs, use [response streaming](../../streaming/output/).

## Test

The HTTP tests create the app with `ResponseBodyExample.application()`. `TestServer` starts it on an available
loopback port and shuts it down when the fixture closes.

The tests compare the exact bytes and `Content-Type` for UTF-8 text, ISO-8859-1 text, and binary output. They check
that `204`, `205`, and `304` send no content when the body is unset and produce `500` when the handler stages a
nonempty body. The `HEAD` test checks that `Content-Length` and `Content-Type` describe the `GET` representation
while the response body is empty.

The size-limit test accepts 0 and 64 bytes. A rejected 65-byte body leaves the staged content and `Content-Type`
intact. Another test checks that `body(...)` leaves the response uncommitted and that changes to the source array
leave the staged bytes intact.
