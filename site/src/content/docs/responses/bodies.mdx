## Description

An HTTP response combines a status, headers and a body. Text helpers encode a Java string; a byte-body helper sends bytes that your application already encoded. `MediaType` describes those bytes, including any declared charset.

This task chooses those representations explicitly. `HttpStatusCodes` and `HttpMethods` name protocol values; `Options` holds the application's buffering limits and `MultipartOptions` configures its separate multipart limits. Response commitment is the point after which sent status, headers or body bytes cannot be replaced.

Use `text(value)` for a UTF-8 response or `text(value, charset)` to select another encoding; Shoostr supplies matching charset metadata. For already encoded bytes, call `body(...)` with the correct `MediaType`. `MediaType.of(...)` normalizes a bare type/subtype and rejects parameters, ranges, wildcards and surrounding whitespace. `withCharset(...)` changes only the label, so your bytes must already use that encoding. Use a String content type for arbitrary parameters.

Text encoding follows `String.getBytes(Charset)`: malformed or unmappable input uses replacement bytes rather than strict validation.
For object output, use an [explicit JSON codec](../../json/codec/).
Set a response status with `status(...)`, using a named `HttpStatusCodes` constant and its `value()` when that makes the result clearer.

A `HEAD` response carries representation metadata without transmitting its body, but the route must be [registered explicitly](../../routing/methods/).
For an empty response with `204`, `205`, or `304`, leave the body unset: Shoostr rejects nonempty content during completion rather than silently discarding it.
`304` belongs to conditional requests, not to a general “nothing to return” response; see the [HTTP status semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5) for that distinction.

## Example

The messages endpoint returns `201` with UTF-8 text, while `/bytes` sends binary data and `/latin1` uses the text helper to select ISO-8859-1.
The DELETE handler returns `204`; the matching `GET` and `HEAD` handlers for `/message` select the same representation, with HEAD suppressing the transmitted bytes.

This example limits finite responses to 64 bytes through `Options.maxResponseBytes()`.
Finite output remains staged until the handler returns successfully, and selecting another body replaces the previous one rather than appending to it.
Keep response access on the handler thread and within its lifetime; Shoostr completes the transfer, so application code must not close `Response`.
See [exception recovery](../../errors/exceptions/) for output replacement before commitment and failures after it.
For file output and its longer transfer lifetime, use the [download recipe](../../resources/downloads/).
For incremental output while the handler runs, use [response streaming](../../streaming/output/).
