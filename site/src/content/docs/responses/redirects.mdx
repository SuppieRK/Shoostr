## Description

Choose the redirect status based on what the destination should receive. Shoostr sends the destination in the
`Location` response header. If the client follows the redirect, the status guides its next request.

| Status | Call | If the client follows |
| --- | --- | --- |
| `302 Found` | `redirect(location)` | The client may change `POST` to `GET`. |
| `303 See Other` | `redirect(location, HttpStatusCodes.SEE_OTHER)` | The client can retrieve the destination with `GET` or `HEAD`. Use it to send a client to a receipt after a `POST`. |
| `307 Temporary Redirect` | `redirect(location, HttpStatusCodes.TEMPORARY_REDIRECT)` | The client repeats the request with the original method and body. |

See [HTTP redirect semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4) for the full status rules.

Choose allowed destinations in application code. `redirect(...)` accepts relative references and non-HTTP schemes.
If a query parameter can suggest a destination, map it to a target your application has approved before calling
`redirect(...)`.

## Example

The `/old` endpoint redirects to `/current`. After `POST /submit`, the client fetches `/receipt` with `GET`.
After `POST /forward`, it sends the original `POST` body to `/receiver`. The example uses constant relative paths
for every destination. A test confirms that adding a destination to the query leaves `/old` pointing to `/current`.

Code after `redirect(...)` still runs. The redirect clears the staged body and headers such as `Content-Type`, and
keeps unrelated headers. The response stays uncommitted, so later code can still change it. Return from the handler
to stop work there. To reject a request before its handler runs, see [request lifecycle hooks](../../lifecycle/hooks/).

If a handler responds before reading the request body, the HTTP/1 connection can close. Following the redirect then
requires a different connection. A client that follows a `307` still sends the original method and body.

## Test

The HTTP tests create the app with `RedirectExample.application()`. `TestServer` starts it on an available loopback
port and shuts it down when the fixture closes.

With automatic following disabled, the tests check each status and `Location` header. When the test client follows
a `303`, the receipt sees `GET`. When it follows a `307`, the receiver sees `POST` and the original body, including
a payload that spans multiple input buffers.

The destination test checks that a query parameter leaves `Location` at `/current`. A test-only handler adds a header
after calling `redirect(...)`. The final response contains that header and the unrelated header set earlier, with an
empty body and no `Content-Type` from the previously staged text.
