## Description

Server-sent events (SSE) let the server send text events over an open HTTP response. An `SseEvent` carries data
and can include a name, an ID and a retry hint. This example sends event frames and shows how to resume a feed
from the cursor a client sends when it reconnects.

1. Register the GET route with `routes.sse(...)`.
2. Validate the request, then call `startEventStream()` to commit the response.
3. Call `send(String)` for data alone or `send(SseEvent)` to include the optional fields.
   Each line of multiline data becomes a separate `data:` field in the same event.

Payloads are UTF-8 text. To encode Java objects with a codec, use [object events](../sse-objects/).

The handler chooses when to call `comment(...)` and `heartbeat()`. Each call flushes its frame, and the client
ignores both when dispatching events. Keep the handler active to continue writing. Shoostr finishes the stream
when the handler returns. See the [streaming lifetime and backpressure rules](../output/).

An open feed occupies its handler task. For long-lived feeds, choose an [execution mode](../../lifecycle/executors/)
and consider a [limit on concurrent streams](../../lifecycle/stream-admission/).

- Keep event names and IDs on one line and omit NUL characters.
- Set a nonnegative retry duration. Shoostr sends it in milliseconds.
- IDs are text. The example interprets them as integer positions in its feed.

When a client reconnects, read its `Last-Event-ID` header from the `Request`. Use it to find the next entry
in the history your application keeps. Your application decides which cursors to accept and what to replay.

## Example

- `/events` sends data, a comment, a heartbeat and named events with IDs and a retry hint. The handler sends
  the same demonstration frames on each request, so a reconnecting browser can receive them again.
- `/replay` uses `Last-Event-ID` as a cursor into a fixed three-entry feed.

| Cursor for `/replay` | Result |
| --- | --- |
| Absent or parses as `0` | Sends all three entries. |
| Parses as `1` or `2` | Sends only the entries after that ID. |
| Parses as `3`, the final entry | Returns `204 No Content` without opening an event stream. |
| Fails to parse as an integer or falls outside `0` through `3` | Returns `400 Bad Request`. The handler throws `BadRequestException` before opening the stream. |

The `204` tells `EventSource` to stop reconnecting.
See the [HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html).
Durable history and duplicate handling belong to the application.
After commitment, a transport failure aborts the stream. See [exception recovery](../../errors/exceptions/).

## Test

`TestServer` starts the application from `SseFeedExample.application()` on an available loopback port
and owns its shutdown. The tests compare complete wire frames, check that a missing cursor starts at the first
entry, and verify that cursor `1` resumes at entry `2`. They also check for `400` on invalid input and a
`204` without a body or `Content-Type` after the last entry.
