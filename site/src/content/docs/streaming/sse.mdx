## Description

Server-sent events (SSE) keep an HTTP response open to send text events to a client. An event stream is the response writer for those frames. `SseEvent` describes event data and optional names, IDs and retry hints.

The handler reads the reconnect cursor from its incoming `Request`; `BadRequestException` rejects an invalid cursor with `400` before the stream starts.

This task first sends frames, then demonstrates how an application can resume its own feed from a supplied cursor. Reconnection is a client behavior; replay requires application-held history and a cursor policy. Validate an unacceptable cursor before starting and committing the event stream.

Register the GET event route with `routes.sse(...)`. Validate input before committing it with `startEventStream()`. Use `send(String)` for data alone or `SseEvent` for names, IDs and retry hints; multiline data is split into frame fields. Payloads are UTF-8 text rather than automatic JSON. Use [object events](../sse-objects/) when a codec should encode the payload.

Comments and heartbeats do not dispatch data events, and each call sends its frame immediately.
They are explicit writes rather than an automatic timer: the handler must remain active for further output, and returning finishes this finite stream.
The [streaming lifetime and backpressure rules](../output/) also apply to event streams.
A handler active for the feed's lifetime occupies its selected task; use
[execution selection and application-owned bulkheads](../../lifecycle/executors/#compose-stream-admission)
for long-lived feeds.

Event names and IDs must fit on one line without NUL characters, while retry durations must be nonnegative and are sent in milliseconds.
The model permits text IDs; the integer cursor used below is this application's replay policy, not a framework restriction.
Shoostr does not retain event history or replay it automatically.

## Example

The `/events` endpoint demonstrates data, comments, a heartbeat and named events with IDs and a retry hint.
The `/replay` endpoint instead uses a fixed three-entry feed: it validates `Last-Event-ID` before opening the stream and sends only entries after that cursor.
An absent cursor starts at the beginning; invalid cursors receive `400`, while cursor `3` receives `204` without opening a stream, telling [EventSource](https://html.spec.whatwg.org/multipage/server-sent-events.html) to stop reconnecting.

This feed is not durable storage and does not promise exactly-once delivery.
The framing-only `/events` endpoint does not implement replay, so a reconnecting browser can receive its demonstration events again.
Once a stream is committed, a transport failure aborts it rather than allowing a replacement HTTP error; see [exception recovery](../../errors/exceptions/) for that boundary.
