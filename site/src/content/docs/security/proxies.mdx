## Description

A reverse proxy can report the original client address and request scheme in forwarding headers. Accept those
assertions only from proxies you control. The physical peer is the host that connects directly to Shoostr.

1. Identify the proxy IP addresses you control. Use a thread-safe, nonblocking predicate to select them.
2. Before startup, call `trustedProxies(...)` with that predicate and one `ForwardedHeaders` family.
   `RFC7239` reads the standard `Forwarded` field and is the default for the one-argument overload.
   `X_FORWARDED` reads the legacy fields. Shoostr uses only the selected family. See
   [RFC 7239](https://www.rfc-editor.org/rfc/rfc7239.html).

Shoostr checks the physical peer's IP address before reading any forwarding headers. It ignores forwarding input from an
untrusted peer.

- From a trusted peer, Shoostr starts at the rightmost entry and walks left through trusted proxy addresses.
  It uses the first untrusted or undisclosed hop, or the leftmost entry if the walk reaches it.
- Configure your edge proxy to remove untrusted forwarding input or append values it observes at its own hop.
  See [RFC 7239's guidance on header integrity](https://www.rfc-editor.org/rfc/rfc7239.html#section-8.1).
- Malformed input in the selected family from a trusted peer receives `400`. In the legacy family, any supplied
  `X-Forwarded-Host`, `X-Forwarded-Proto` or `X-Forwarded-Port` list must have the same number of entries
  as `X-Forwarded-For`.

## Example

`GET /metadata` returns the resolved client address from `clientAddress()` and the proxy-aware URL from
`effectiveUrl()`. The factory copies the supplied set of trusted proxy addresses before startup and uses
that fixed set for trust checks. In the tests that exercise both header families, the fixture trusts
`127.0.0.1` and selects `RFC7239` or `X_FORWARDED` for each run.

| Accessor | Reports |
| --- | --- |
| `isSecure()` | Whether the direct connection to Shoostr uses TLS. |
| `isEffectivelySecure()` | Whether the trusted forwarded protocol is HTTPS, when supplied. Otherwise it reports direct transport security. This is the accessor used by the pac4j adapter. |

When a trusted proxy receives HTTPS and forwards over plain HTTP, an accepted HTTPS assertion makes
`isEffectivelySecure()` return `true`. The plain connection makes `isSecure()` return `false`. Use these accessors for
security checks. The scheme in `effectiveUrl()` can also come from the request's URL text. See
[request metadata](../../request/metadata/) and the [pac4j adapter](../pac4j/).

## Test

The tests start `TrustedProxyExample.application(trustedPeers, family)` with `TestServer` on an available
loopback port. The fixture owns application shutdown.

- Each header family supplies its own client address and URL, even when the other family is present.
- The trust walk stops at the first untrusted hop. Forwarding input from an untrusted physical peer is ignored.
- The tests assert `400` for malformed forwarding from a trusted peer and for legacy lists with different hop counts.
- Adding a trusted address to the original set after application construction leaves the configured trust set intact.

The HTTP tests assert `transportSecure=false` and `effectiveSecure=true` for a trusted HTTPS assertion over
a plain connection.
