## Description

Use Shoostr's `pac4j` adapter with a configured pac4j `DirectClient` when credentials arrive with each request rather than through a browser redirect and callback flow.

:::note[Libraries required]
- `io.github.suppierk:shoostr-pac4j` — Shoostr's pac4j adapter.
- `org.pac4j:pac4j-http` — the `DirectBasicAuthClient` used in this example.
:::

The [`pac4j-http` client reference](https://www.pac4j.org/6.5.x/docs/clients/http.html) describes the available credential formats.
Configure the client's authenticator before constructing `Pac4j` and do not mutate the client while the application serves requests.

The adapter extracts and validates credentials, requires an unexpired profile, publishes its principal, and then calls the configured authorizer.
Missing or rejected credentials receive the configured `401` challenge, while a verified profile denied by the authorizer receives `403`.
Install the adapter and select that same instance on the protected group, following the [route authentication](../authentication/) selection rules.

## Example

The `/accounts/me` route returns the validated profile's name, and `/accounts/admin` additionally requires its `administrator` role.
The explicit authenticator checks development-only accounts and assigns that role to `admin`; these fixed passwords are local fixtures, not a production identity store.
Use HTTPS for HTTP Basic credentials outside a controlled local test and replace the fixture validation with your actual account policy.

The adapter is stateless: it authenticates each protected request without creating a session or saving a profile in one, even when the application separately enables sessions.
It does not implement pac4j's indirect-client login or callback flow.
When a trusted proxy terminates TLS, pac4j's security context uses `request.isEffectivelySecure()`; configure [proxy trust](../proxies/) explicitly rather than trusting a forwarded scheme from any client.
