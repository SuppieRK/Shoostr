## Description

Use Shoostr's `Pac4j` adapter when each protected request carries its own credentials. A pac4j `DirectClient`
reads those credentials from the current request and validates them to obtain a user profile. Browser login flows
with redirects and callbacks use indirect clients and require a separate integration.

:::note[Libraries required]
- `io.github.suppierk:shoostr-pac4j` — Shoostr's pac4j adapter.
- `org.pac4j:pac4j-http` — the `DirectBasicAuthClient` used in this example.

See [Maven and Gradle installation](../../start/libraries/) for published Shoostr coordinates.
:::

1. Configure the direct client's authenticator. For client types and credential formats, see the
   [pac4j 6.6 HTTP client reference](https://www.pac4j.org/6.6.x/docs/clients/http.html).
2. Create `Pac4j` with the configured client and a `WWW-Authenticate` challenge. This example also passes an
   authorizer for the role check. Keep the client configuration fixed while the application serves requests.
3. Call `lifecycle.withExtension(authentication)` on the `Lifecycle` supplied to the route or group configuration
   callback. Shoostr sets up the adapter on first selection. For inheritance and exclusions, see
   [route authentication](../authentication/).

The adapter rejects duplicate `Authorization` fields before it calls the client. For requests that pass that
check, it takes these steps in order.

1. Ask the direct client to extract and validate the credentials.
2. Obtain a profile from the validated credentials and check that it is unexpired.
3. Attach the profile's principal to the request.
4. Pass the profile to the configured authorizer.

Missing or rejected credentials and missing or expired profiles receive `401` with the configured challenge.
An authorizer that denies a verified profile causes `403`.

## Example

The example selects one adapter for the `/accounts` group. The authenticator verifies the local accounts and
gives `admin` the `administrator` role.

| Route | Result |
| --- | --- |
| `/accounts/me` | Returns the authenticated caller's name. |
| `/accounts/admin` | Returns `permitted` for a caller with the `administrator` role. |

The fixed passwords are for local tests. Replace the fixture with your application's credential validation.
Use HTTPS for HTTP Basic credentials outside a controlled local test. See the [HTTP Basic security considerations](https://www.rfc-editor.org/rfc/rfc7617.html#section-4).

Session and proxy settings belong to the application.

- The adapter authenticates each protected request without creating a session or storing a profile in one,
  even when the application enables sessions.
- The pac4j security context uses `request.isEffectivelySecure()`. It uses the trusted forwarded protocol
  when available and checks direct TLS otherwise. If a proxy terminates TLS, configure trust explicitly
  before relying on the forwarded scheme. See [proxy trust](../proxies/).

## Test

The tests start `Pac4jAuthenticationExample.application()` with `TestServer` on an available loopback port.
The fixture owns application shutdown.

The tests send HTTP Basic credentials and check the resulting principal and role decision. Requests with
missing, rejected or duplicate credentials receive `401`. A verified reader receives `403` at
`/accounts/admin`, and a verified admin succeeds. With sessions enabled, the tests check that authentication
sets no session cookie and a later request still has no session.
