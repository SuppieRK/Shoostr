## Description

Authentication verifies credentials and establishes a request's identity. Authorization then decides whether that identity may perform an operation. In Shoostr, a principal is the identity value attached to a request after your authenticator has verified it.

An installed provider is an object that contributes reusable application behavior. The provider interface is `Extension<C>`, where `C` names its route-settings type. `AuthenticationExtension` is the base for a provider that also acts as the request's authentication handler. Route callbacks receive an `Extensions` configuration object; selecting the installed authenticator there protects that route or group.

The authenticator callback receives the incoming `Request` and outgoing `Response`, just as an endpoint handler does.

This task distinguishes missing or invalid credentials from an authenticated permission denial. The example's credential lookup is a test fixture, rather than a production identity system.

Implement the authenticator with `AuthenticationExtension`, which combines `Extension<AuthenticationExtension>` provider behavior with a `Handler`. The provider participates in application lifetime and supplies a dedicated authentication step before endpoint work.

Implement `handle(request, response)` to validate credentials and establish the request's identity.
Shoostr supplies the final `configure(...)` implementation; selecting the instance with `extensions.with(authentication)` requires authentication in that scope.
The selected authenticator runs before local and application admission hooks and the endpoint handler.

Install an instance with `app.authentication(authentication)`; `app.extensions(...)` rejects authentication extensions.
In the route or group configuration callback, use the supplied [`Extensions`](../../extensions/route-metadata/#description) object to select that same instance through `extensions.with(authentication)`.
Installation alone does not protect a route, and a group's selection is inherited by its child routes.
To protect registered endpoints by default, select the authenticator in `app.configureExtensionsDefaults(...)` before registering routes, then use `extensions.without(authentication)` on a public endpoint or group.
A deeper `with(authentication)` restores the same owner; exclusion does not permit substituting another authenticator.
Several authenticators can be installed in one application, but each endpoint can require only one distinct instance; conflicting selections are rejected during registration.

Validate the supplied credentials before assigning `request.principal(...)`, because a principal is the identity established by your policy, not proof that Shoostr has independently checked a token.
Use `AuthenticationRequiredException(challenge)` for a `401` response with `WWW-Authenticate`, and `ForbiddenException` when a verified identity lacks permission for the operation.

## Example

The example leaves `/public` unprotected, requires an identity for `/private/me`, and permits only the `admin` identity at `/private/admin`.
Its fixed bearer tokens are development fixtures, not production secrets or an OAuth server; replace that lookup with real credential validation, including the validity and permission checks your token format requires.
Protect bearer tokens with HTTPS outside a controlled local test, as described in [Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1).

The authenticator accepts one Authorization field, rejects ambiguous credentials, and publishes a principal only for a recognized token.
Shoostr owns the installed authenticator's lifecycle; the handler reads the verified principal without retaining its live request.
For a configured third-party direct client and role authorizer, use the [pac4j adapter](../pac4j/).
For browser login backed by a native session, see [Log in and log out with session cookies](../login-logout/).
