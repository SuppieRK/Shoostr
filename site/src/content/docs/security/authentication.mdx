## Description

On a protected route, missing or invalid credentials receive a `401` challenge. If the caller has a verified identity
and lacks permission for the operation, return `403`.

Authentication verifies credentials and establishes who is making the request. Your authenticator attaches that
identity to the request as a principal. Authorization decides what the principal may do.

Implement `handle(request, response)` on an `AuthenticationExtension`. Shoostr calls it with the live `Request`
and `Response` before local and application admission hooks and the endpoint handler.

1. Validate the credentials in `handle(...)`. If they are missing or invalid, throw
   `AuthenticationRequiredException(challenge)` to send `401` with a `WWW-Authenticate` header.
2. Assign the verified identity with `request.principal(...)`. The principal records the identity your
   authenticator established. Your code is responsible for verifying the credentials.
3. Check whether that identity may perform the operation. In this example, the admin endpoint throws
   `ForbiddenException` to return `403` when a verified caller lacks permission.

Shoostr supplies the final `configure(...)` implementation. The authenticator combines `ApplicationExtension`
for application-wide defaults with `RouteExtension` for selection on a route or group.

Use the [`Lifecycle` supplied to a route or group configuration callback](../../extensions/route-metadata/#description)
to select the authenticator for that scope.

- Call `lifecycle.withExtension(authentication)` to protect the route or group. Shoostr sets up the authenticator
  on first selection and owns its cleanup. Child routes inherit the group's selection.
- To protect routes by default, call `app.withExtension(authentication)` before registering routes. Call
  `lifecycle.withoutExtension(authentication)` on a public route or group to exclude that instance.
- Call `lifecycle.withExtension(authentication)` in a descendant to restore the same instance. The original
  instance remains the only authenticator that branch can select after exclusion.
- Separate scopes can use different authenticators. Each endpoint can require at most one instance,
  and Shoostr rejects conflicting selections during registration.

## Example

The example protects the `/private` group and checks for the `admin` identity on one of its endpoints.

| Route | Access |
| --- | --- |
| `/public` | Public |
| `/private/me` | Any identity verified by the authenticator |
| `/private/admin` | Only the verified `admin` identity |

The authenticator requires exactly one `Authorization` header and assigns a principal only for a recognized bearer
token. The endpoint handlers read that principal during the request.

The fixed bearer tokens are for local tests. Replace the lookup with credential validation and the permission checks
your token format requires. Serve deployed bearer-token requests over HTTPS. See [Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html#section-5.3).

For a configured credential client and role authorizer, see the [pac4j adapter](../pac4j/).
For browser login backed by a native session, see [log in and log out with session cookies](../login-logout/).

## Test

The tests start `RouteAuthenticationExample.application()` with `TestServer` on an available loopback port.
The fixture owns application shutdown.

HTTP requests with missing, invalid or duplicate credentials get a `401` challenge on both private routes.
A valid token identifies the caller at `/private/me`. On `/private/admin`, a verified reader gets `403` and
a verified admin succeeds. The public endpoint still responds to a request with invalid credentials.
The tests also verify mixed-case `Bearer` and multiple spaces between the scheme and token.
