## Description

Use a session cookie to keep a browser signed in between requests. Your handlers verify credentials,
establish the account identity in the session and end that session at logout. The example uses three
Shoostr features.

- The native session stores account state and preferences across requests. See [sessions](../sessions/).
- The `AuthenticationExtension` reads the account from the session and sets the request's principal.
  See [authentication](../authentication/).
- The `Csrf` extension checks a session-bound token and source origin on writes. See [CSRF protection](../csrf/).

The example sets authentication and CSRF protection as application defaults with `withExtension(...)`.
Both `/login` routes exclude authentication through their `Lifecycle` configuration so an anonymous
browser can log in. The login POST still requires CSRF verification.

Pass a thread-safe credential verifier to `LoginLogoutExample.application(authenticate)`. It returns the
canonical account ID for valid credentials. The caller owns the verifier and its lifetime. The example
stores the returned account ID in the session and keeps the submitted credentials within the request.

| Exception | Status | When it applies |
| --- | --- | --- |
| `BadRequestException` | `400` | A credential field is missing or repeated, or the theme is invalid. |
| `UnauthorizedException` | `401` | Credentials are rejected or the request needs a valid authenticated session. |
| `ForbiddenException` | `403` | CSRF verification rejects the request. |
| `ConflictException` | `409` | The login handler finds an account already assigned to the session. |

Complete each session transition before the response commits. Use HTTPS directly or through an
[explicitly trusted HTTPS proxy](../proxies/). Serve untrusted executable HTML and JavaScript from a
separate origin and host with host-only cookies. See the [browser trust guidance](../csrf/#description).

## Example

1. Request `GET /login` to obtain a CSRF token. It creates an anonymous session if needed and sets the
   default theme only when the session has none.
2. Send `POST /login` with exactly one `username` and one `password` in the form body. Include the current
   session cookie, CSRF token and an accepted source origin.
3. After CSRF admission, the handler verifies the credentials. It then checks under the session lock that
   the session is still anonymous. It renews the identifier, creates the token for the new identifier,
   stores the account ID and returns the new token. The existing theme survives the transition.
4. Use the replacement cookie and token for writes such as `POST /account/theme`. Use `GET /account/me`
   to read the account and theme.

The verifier runs outside the session lock. If another login assigns the account while verification is
running, the recheck returns `409`. Token responses and successful account responses use
`Cache-Control: no-store` to instruct HTTP caches to skip storing them.

To log out, send `POST /account/logout` with the current cookie, token and an accepted source origin.
The handler invalidates the session, including its expected CSRF token, and sends an expired session cookie.
To log in again, start with a fresh `GET /login` request.

Invalidation takes effect even if the logout response is lost. The browser may retain the old cookie,
and the server rejects that cookie and token on later requests to the account routes. Renewal and
invalidation apply to later admission checks. Requests that already passed admission may continue,
and existing WebSockets have their own connection lifetime.

## Test

The tests start `LoginLogoutExample.application(authenticate)` with `TestServer` over loopback HTTPS.
The fixture uses a temporary certificate, takes a test credential verifier and owns application shutdown.

- Login renews the session identifier, replaces the token and retains the theme.
- Missing or duplicate form fields trigger `400`. Invalid proofs and origins get `403` before the verifier runs.
  After a credential failure, the anonymous cookie and token still work for a retry.
- The concurrency test releases two credential checks together. One login succeeds and the other receives `409`.
- Repeated account reads carry `Cache-Control: no-store`. Logout expires the cookie. Requests using the
  old cookie receive `401`, and a fresh session supports a later login.
