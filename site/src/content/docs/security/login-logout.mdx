## Description

A browser login joins several responsibilities: verify credentials, establish authenticated session state and protect cookie-backed writes. Logout ends that state. Your application coordinates those steps rather than asking one callback to stand in for the entire policy.

An HTTP session retains state across requests. `AuthenticationExtension` verifies the request's session identity, while the installed `Csrf` provider checks a session-associated proof for writes. The route's `Extensions` configuration selects the required provider. `Cookie` and `HttpHeaders` describe the protocol metadata exchanged with the browser.

The handlers receive the incoming `Request` and outgoing `Response`. `BadRequestException` rejects malformed input with `400`, `UnauthorizedException` rejects failed credentials with `401`, and `ConflictException` returns `409` when login would replace an existing account.

The login and logout handlers coordinate those responsibilities. The credential verifier remains application-owned.

Coordinate [sessions](../sessions/), [CSRF protection](../csrf/) and [authentication](../authentication/) in application handlers. No provider performs login or logout automatically. Renewing the native session ID rejects its old CSRF proof; invalidating the session removes the expected value. The example delegates credential checks to your existing thread-safe verifier and uses the canonical account ID it returns. It stores no passwords and owns no verifier lifecycle.

Start with `GET /login`, which returns a CSRF token and creates an anonymous session without replacing existing state.
Submit one username and password in the body of `POST /login`, together with the current cookies, proof and accepted source origin.
After credential verification succeeds, the handler renews the session identifier and prepares a fresh session-bound proof before publishing the account identity, then returns the proof.
Use the replacement session cookie and proof for protected writes; repeated login is rejected so one account cannot silently replace another in the same session.
Successful account responses use `Cache-Control: no-store` to prevent HTTP caches from retaining the identity or preferences.

`POST /account/logout` invalidates the native session and expires its cookie. Obtain a new proof and anonymous session in a later request before logging in again.
The server-side invalidation remains effective even if the browser never receives the logout response, but cookie changes and network delivery are not a transaction that can roll back a completed transition.
Restoring the old cookie and proof does not restore an invalidated native session.
Renewal and invalidation affect later admission; they do not cancel work that another request has already been authorized to perform or close an existing WebSocket.

Use HTTPS directly or through an [explicitly trusted HTTPS proxy](../proxies/), and keep every transition before the response commits.
Do not host untrusted executable HTML or JavaScript on this trusted origin; use a separate origin and host with host-only cookies, following the [browser trust guidance](../csrf/#description).
