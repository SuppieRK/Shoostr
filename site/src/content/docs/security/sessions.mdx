## Description

Use an HTTP session to keep application state across requests under a session identifier. A request attribute
lasts for one exchange. A principal identifies the caller. If the session holds account state, verify the
caller's identity with [authentication](../authentication/).

This example uses Jetty sessions to store a theme preference. It creates a session on demand, renews its
identifier and invalidates the stored state.

- Call `app.sessions()` to enable sessions or `app.sessions(handler -> ...)` to configure Jetty's handler.
- Shoostr uses one application-level session handler for ordinary requests. It creates a session on request
  from application code. Use the standard request API to access it.

| Method | Result |
| --- | --- |
| `getSession()` | Reads an existing session without creating one. Returns an empty `Optional` when there is no session or sessions are disabled. |
| `getOrCreateSession()` | Returns the current native `Session`, even after commitment. Creating a missing session requires an open response and available session handling. Otherwise creation throws `IllegalStateException`. |
| `renewSessionId()` | Changes an existing session's identifier, retains its attributes and updates the cookie before the response commits. |
| `session.invalidate()` | Invalidates the session and clears its stored state. |

The configuration callback receives the native `SessionHandler` after the `modifyServer(...)` callbacks and
before startup. Configure cookie attributes, idle limits, and the cache and data store there. Shoostr manages
these components, so preserve the handler's server and child wiring. See the
[Jetty session reference](https://jetty.org/docs/jetty/12.1/programming-guide/server/session.html).

Leave the cookie domain unset for a host-only cookie. When a proxy terminates TLS and forwards plain HTTP to
Jetty, use `handler.setSecureCookies(true)` to mark the cookie `Secure` on every response that issues it.
Trusted forwarding alone leaves Jetty's native cookie policy as configured.

Pass an existing private directory outside any public resource mount to `SessionExample.application(directory)`
and use serializable session attributes. Keep the store directory and native context configuration stable
across restarts. Use distinct directories for independent file stores. Closing the application stops the
session components and leaves the caller-owned store files in place.

## Example

The example issues a host-only `PREFERENCES` cookie with `Secure`, `HttpOnly` and `SameSite=Strict`. The
900-second `Max-Age` controls how long the browser retains the cookie. A separate 900-second idle limit controls
how long Jetty keeps an unused session valid.

| Route | Behavior |
| --- | --- |
| `GET /preferences/session` | Creates a session if needed and sets the theme to `dark` if no theme is set. |
| `GET /preferences/state` | Uses `getSession()` to read the current theme or return `absent`. |
| `POST /preferences/renew` | Changes the identifier and retains the attributes. With no session, `NotFoundException` produces `404`. |
| `POST /preferences/reset` | Invalidates the session if present and returns `cleared`. |

After invalidation, you can call `getOrCreateSession()` in the same request before the response commits. The
replacement has a fresh identifier and no stored attributes. Access session state during request handling and
keep compound attribute updates safe for concurrent requests.

Protect cookie-authenticated writes with [CSRF checks](../csrf/) even when using `SameSite`. For credential
verification, session renewal, fresh CSRF token delivery and logout, see
[log in and log out with session cookies](../login-logout/). Serve mutually untrusted browser applications from
separate hosts with host-only cookies. See the [browser trust boundary guidance](../csrf/#description).

## Test

The tests start `SessionExample.application(directory)` with `TestServer` on an available loopback port.
The fixture owns application shutdown.

The tests check the cookie attributes and show that a request without the cookie sees no stored preference.
They verify that renewal preserves state under the new identifier and that the old cookie loses access after
renewal or invalidation. Renewal without a session returns `404`, and an invalid store path fails before
startup. A second application using the same temporary directory restores the preference.

The tests send the cookie explicitly over loopback HTTP to verify server behavior. Browser delivery of a
`Secure` cookie in a deployed application requires HTTPS.
