## Description

When a browser sends authentication cookies automatically, require a session-bound token for requests that change
state. Cross-site request forgery (CSRF) protection checks that token and the request's source origin before the
handler runs. This example uses `Csrf` to protect writes to a session preference and renewal of the session identifier.

1. Enable [native sessions](../sessions/). Startup fails if a protected endpoint has no session support.
2. Create one `Csrf` instance. In the route or group configuration callback, select it on the supplied
   `Lifecycle` with `lifecycle.withExtension(csrf)`. Shoostr handles shared setup on first selection.
3. To protect registered routes by default, call `app.withExtension(csrf)` before registering them. Call
   `lifecycle.withoutExtension(csrf)` on routes or groups you want to exclude.

Child routes inherit the protection. Selecting the same instance again keeps one check. After an exclusion,
a descendant can restore only the original instance.

Deliver the value from `csrf.token(request)` in a response body or page. On an unsafe request, send it once in
an `X-CSRF-Token` header or a `_csrf` form field. A request that uses both channels fails even if the values match.
Shoostr stores the expected token in the native session and binds it to the current identifier. The session
cookie carries that identifier. Protect it with HTTPS and suitable cookie attributes. Keep token responses out
of shared caches and tokens out of URLs. See the
[OWASP synchronizer-token guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#synchronizer-token-pattern).

A protected unsafe request needs an existing session, one valid token and an accepted source origin. By default,
the source must match the effective target origin. Shoostr checks `Origin` first and uses `Referer` only when
`Origin` is absent. It rejects missing, malformed, ambiguous or untrusted source information.

To allow additional browser origins, use `Csrf.builder().trustedOrigins(...)` with exact HTTP(S) origins.
Supply a first origin followed by optional varargs or pass a set. The builder validates them on `build()`.
Cross-origin browser scripts also need a [CORS policy](../cors/).

| Operation | Token behavior |
| --- | --- |
| `csrf.token(request)` | Creates a session if needed and returns a stable, unpredictable token for its current identifier. |
| `request.renewSessionId()` | Keeps the session attributes and invalidates the old token immediately. The next `token(request)` call creates a token for the new identifier. |
| `session.invalidate()` | Removes the session and its expected token. Obtain a new session and token before the next protected write. |

Reuse a token while its issuing session identifier remains valid. Persistence and consistency across application
instances depend on the configured native session store.

Add authentication to routes that require a verified identity. It runs before local admission hooks, including
CSRF. A public login endpoint can exclude authentication and still verify CSRF before its credential handler.
See the [login and logout recipe](../login-logout/) for credential verification and session transitions.

:::caution[Keep untrusted scripts on a separate host]

Serve executable HTML and JavaScript on the application's trusted origin only if you trust that code. Same-origin
scripts can obtain tokens and make requests with the user's cookies across route groups, extension instances and
cookie names.

Use separate origins on separate hosts with host-only cookies for mutually untrusted applications. Cookie scope
spans ports. Cookie `Path` controls where a browser sends the cookie, and same-origin scripts can still make requests
to those paths. See [RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5).

:::

## Example

| Route | Behavior |
| --- | --- |
| `GET /csrf-token` | Returns the session token with `Cache-Control: no-store`. |
| `GET /preferences` | Reads the session's theme or returns `unset`. |
| `POST /preferences` | Verifies CSRF, then accepts `light` or `dark`. The handler throws `BadRequestException` for invalid or missing input, which returns `400`. |
| `POST /session/renew` | Verifies CSRF against the current session, renews its identifier, and returns a fresh token with `Cache-Control: no-store`. |

Keep state changes on unsafe methods. CSRF verification passes `GET`, `HEAD`, `OPTIONS` and `TRACE` without
checking a token.
