## Description

Use `McpOperationLimits` from `shoostr-mcp` to bound work within an admitted MCP session, independently of [session allocation limits](../security/).
Configure one policy for ordinary requests and incoming notifications, and a separate policy for protocol replies and `notifications/cancelled`.
Both policies expose total, per-owner and per-session capacities and an absolute timeout.
Each `Mcp` instance has independent budgets; these are not JVM-wide or distributed quotas.

For blocking Java work, return or compose `work.call(...)` from a native async handler.
Shoostr runs the callable on its owned virtual-thread executor, outside Reactor's shared scheduler.
Returning a publisher from a native async handler preserves its operation context; invoking `work.call(...).block()` inside a native synchronous handler does not transfer that ownership.
Use borrowed `mcp.work()` when registering additional native async handlers after construction.

Existing factories automatically receive finite admission limits.
Their raw native callbacks, arbitrary publishers and independently started tasks remain application-owned.
Managed execution does not provide dedicated CPUs, JVM carriers or forced termination of arbitrary Java code.
These budgets do not reserve HTTP workers for long-lived streams; choose [endpoint execution](../../lifecycle/executors/) and connection capacity separately.

## Example

This public status tool checks client reachability, then reads a nonsecret status through a blocking callable.
The ping reply uses reserved control capacity even while the originating request occupies an ordinary slot.
Replace the status supplier with your blocking operation, and [protect the endpoint](../security/) before exposing private state.
The shared `public` owner means all callers in this demonstration share one owner quota.

Ordinary capacities apply to two separate counts: admitted operations and managed callables.
For example, a session ceiling of two permits up to two admitted operations and, independently, two managed callables.
Several parallel callables within one operation each consume execution capacity.
An operation stays charged until native ownership ends and all its started managed callables actually exit.
These ceilings bound counts, not the bytes retained by each operation.

Excess initial admissions receive HTTP 429 for owner/session capacity or 503 for total capacity, before native callback execution.
There is no extra admission waiting queue.
If an admitted operation cannot start another managed callable, its publisher fails with a busy error; an unhandled failure becomes JSON-RPC error `-32000`.
Applications can handle that publisher failure explicitly.

The deadline starts at admission, includes scheduling delay, and never resets on progress.
Expiry attempts one correlated JSON-RPC timeout error (`-32001`), then ends the response stream; delivery failure falls back to failing/closing the stream.
Accepted notifications already returned HTTP 202, so subsequent processing failure or expiry is asynchronous.
The control reserve is also finite and can reject excess traffic.

`notifications/cancelled` targets an active request in the same session and suppresses its response when cancellation wins.
Unknown, completed or malformed targets are ignored.
A timeout or cancellation requests interruption but keeps started managed work charged until it exits.
For the supported `2025-11-25` protocol, HTTP disconnection alone does not cancel session-owned work.
Neither cancellation nor a timeout reverses side effects; retry only when the application operation supports it.

The example uses explicit, small capacities to demonstrate behavior.
Library defaults for each policy are 256 total, 64 per owner, 16 per session and five minutes; these are tunable starting values, not measured deployment capacity.
The [client-interaction recipe](../interactions/) distinguishes the total operation deadline from each individual client-reply timeout.

They verify the status result, reserved reply progress, immediate overload rejection, matching cancellation, and a correlated timeout.
A controlled callback deliberately ignores interruption so the test can prove that replacement work remains rejected until the callback actually exits.
