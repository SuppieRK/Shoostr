## Description

Use native MCP callbacks to request input from the connected client and notify subscribers when a resource changes.
Check the client's declared capabilities before requesting [form elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) or [sampling](https://modelcontextprotocol.io/specification/2025-11-25/client/sampling): the client controls its user interface, model access and approval policy.
Sampling requests a generated message from that client; Shoostr does not supply a model provider.

This public demonstration shares only a nonsecret service status.
Both the MCP endpoint and the HTTP status-update handler are unauthenticated, so protect both before introducing private operations or user-specific data; the [MCP security recipe](../security/) covers verified identity and session ownership.
The audience form asks for a choice between developers and operators, never passwords, API keys or access tokens.

## Example

The tool captures the current status, asks the client to choose an audience, then requests a summary using that choice.
It preserves a declined or cancelled form response without sampling afterward, validates accepted input, and rejects a blank or non-text summary.
The server's two-minute timeout bounds its wait for each client reply; the client can impose its own shorter timeout.
The adapter's default five-minute absolute operation deadline leaves room for the two sequential interactions and processing; [configure it explicitly](../operations/) for longer workflows.

MCP logging and progress notifications go to the initiating client, not every session.
Progress uses the caller's supplied `progressToken`, with updates for starting, accepting the audience and completing the summary; a call without that token produces no progress notifications.

The HTTP handler strips surrounding whitespace and accepts one nonblank status line with a maximum length of 80 UTF-16 code units.
After updating the shared value, it uses borrowed `mcp.server()` management access to notify subscribers of `status://current`.
The resource supports subscriptions, not resource-list changes, and an update notification signals a change rather than carrying a durable history; a later read can see a newer value if updates overlap.
Shoostr owns native server cleanup, so do not close that borrowed server independently.

An elicitation `CANCEL` response ends this example's summary workflow; it is not forced cancellation of arbitrary Java work.
Shoostr handles matching `notifications/cancelled` requests in the adapter even though SDK 2.1.0 has no native handler.
A disconnected HTTP stream does not cancel session-owned native work; operation deadlines, explicit session deletion and application shutdown also request cancellation.
The [operation recipe](../operations/) explains managed execution and capacity retained until an interrupted callback actually exits.
External operations cannot be forcibly stopped by cancelling their publisher.
The [transport recipe](../server/) also explains the absence of SSE replay.

For additional native SDK features, see the protocol references for [client roots](https://modelcontextprotocol.io/specification/2025-11-25/client/roots), [prompt and resource-template argument completion](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/completion), and [URL elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation).
Roots do not enforce a filesystem sandbox, and accepting URL elicitation records consent rather than proving that an external flow completed.
