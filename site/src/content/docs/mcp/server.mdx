## Description

Expose a catalog that Model Context Protocol (MCP) clients can discover and use. Shoostr's optional `shoostr-mcp`
integration connects a native MCP Java SDK server to a Streamable HTTP endpoint. This example serves a deliberately
public catalog. See [Maven and Gradle installation](../../start/libraries/) for the `shoostr-mcp` coordinates.

| Capability | What clients get |
| --- | --- |
| [Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | Named operations they can call. |
| [Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources) | Context they read by URI through MCP. |
| [Prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts) | Reusable messages. The client decides whether to send them to a model. |

Set up the server and its HTTP mount explicitly.

1. Set the transport admission and identity policy with `McpHttpSecurity`. The identity callback supplies a
   detached `McpIdentity` for an admitted caller. Configure authentication on the enclosing route group when required.
2. Pass the policy and a native server factory to `Mcp.sync(security, factory)` or `Mcp.async(security, factory)`.
   Declare the capabilities and callbacks inside the factory.
3. Mount the provider once on a literal group path with `routes.path("/mcp", mcp::routes)`. The helper registers the
   protocol handlers and activates the provider on those routes. Route activation sets up the shared transport.

Use `McpSessionLimits` to change the default capacity of 1,024 sessions overall and 32 per owner, or the 30-minute
idle timeout. Pass it to `Mcp.sync(security, limits, factory)` or `Mcp.async(security, limits, factory)`. The provider
copies the limits before invoking the factory. Session limits count allocations, including initialization and cleanup.
Your application sets its own limits for work performed by callbacks.

The adapter supports stateful Streamable HTTP. These examples target the `2025-11-25` protocol revision.
SSE streams deliver live events. SSE replay and `Last-Event-ID` recovery are unavailable.

## Example

Both factories expose the same fixed catalog. The `greet` tool returns `Hello from Shoostr`, `guide://start` supplies
context, and `explain` returns a prompt message. Choose either factory for your application. Synchronous callbacks
return native results directly. Asynchronous callbacks return Reactor `Mono` values. Declare the capabilities the
server provides. This catalog disables subscriptions and catalog-change notifications.

The public policy accepts non-browser clients without an `Origin` header. When the header is present, only
`https://client.example` is allowed. Shoostr checks the origin before authentication. The example uses one shared session owner
and leaves token expiry unset because the catalog holds only public data. For private operations, see
[protect MCP identity, permissions and sessions](../security/). For sampling, elicitation and subscriptions, see
[request MCP client input and enable resource subscriptions](../interactions/).

Keep server ownership, HTTP execution and callback work separate.

- Create a separate `Mcp` instance per application. Shoostr closes its native server and transport. Use `mcp.server()`
  for borrowed management access and leave closure to Shoostr.
- The SDK controls native callback scheduling. Use its transport context and detached values in callbacks. Live
  Shoostr requests and responses stay with the HTTP handler.
- `mcp.routes(group, httpExecutor)` uses the supplied executor for the matched GET, POST and DELETE handlers.
  Streams that occupy every worker in a finite pool can delay replies and session deletion before their handlers run.
  The caller owns the executor and keeps it available until the application closes and outstanding work finishes.
  See [endpoint execution](../../lifecycle/executors/).
- Each stream mailbox holds up to 64 queued frames. Validate the size of application results before returning them
  because the queue bounds frame count only. A mailbox already closed or full rejects a send before JSON
  serialization. A concurrent close or competing send can still cause rejection after serialization.
