## Description

Verify the caller on every request to a protected MCP endpoint. A session ID identifies protocol state.
Authentication verifies the caller's credentials, and authorization checks which operations that identity may perform.

:::note[Libraries required]
- `io.github.suppierk:shoostr-mcp` provides Shoostr's MCP server and Streamable HTTP integration.

See [Maven and Gradle installation](../../start/libraries/) for published Shoostr coordinates.
:::

This example adds identity and session policy to the [MCP transport](../server/).

| Role | Provided by |
| --- | --- |
| Authenticate HTTP requests | An `AuthenticationExtension` selected on the MCP route group. |
| Mount the SDK server over HTTP | The `Mcp` provider. |
| Admit origins, extract identity and authorize messages | `McpHttpSecurity`, which carries a detached `McpIdentity` into message processing. |
| Limit session allocation and idle lifetime | `McpSessionLimits`. |

Check credentials on every POST, GET and DELETE and bind the session to the verified owner.

1. Implement the authenticator. Its `handle(request, response)` method receives the live `Request` and `Response`.
   For missing or invalid credentials, throw `AuthenticationRequiredException` to send a `401` with `WWW-Authenticate`.
2. Select it with `lifecycle.withExtension(authentication)` on the `Lifecycle` supplied to the group callback.
3. Configure `McpHttpSecurity` with the exact allowed origins, an identity extractor that reads the authenticated
   principal, and a policy that checks incoming messages before SDK dispatch.

The example serves only the MCP endpoint. It uses fixed development Bearer credentials and a local registry in place
of cryptographic token verification. The HTTPS metadata URL is a placeholder for discovery.

Before using private data, verify each token's issuer, intended audience, validity and permissions. For OAuth
deployment, configure discovery metadata and an authorization server that clients can reach.
[MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) ·
[MCP security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

## Example

The credential registry sets each token's expiry once when the application is created.

- The authenticator puts immutable claims in the principal. The identity extractor passes those claims in detached
  transport context so the SDK callback can read them during a tool call.
- The session owner key encodes the subject and client separately. It stays the same when scopes or expiry change,
  so a refreshed credential for that owner can use the session. If you accept multiple issuers, include the verified
  issuer in the key.

Origin admission and scope checks happen before the SDK handles a message.

- Shoostr checks `Origin` before authentication. Requests without that header pass origin admission. A present
  value must match `https://client.example` in this example.
- Every mounted transport method requires `mcp:access`. The message policy also checks the current token's
  `tools:read` scope for tool discovery and calls.
- Insufficient scope returns HTTP `403` with a `WWW-Authenticate` challenge naming the required scope and metadata
  URL. Native tool errors come from callbacks after dispatch.

The example allows four session allocations overall, two per owner, and a ten-second idle timeout. These small
limits make capacity and expiry visible in the tests.

- Initialization and native cleanup count against capacity. An expired session can become unavailable before
  cleanup releases its reservation.
- An open stream ends when its credential reaches its fixed expiry. Fresh credentials for the same owner can
  still use the session.
- Idle expiry and explicit deletion end the session. Capacity becomes available when native cleanup finishes.

Session limits govern native session allocation. Set limits for callback work separately in your application.

## Test

The tests start `McpSecurityExample.application()` with `TestServer` on an available loopback port. The fixture owns
application shutdown.

- The native SDK client calls the `identity` tool and receives the subject and client from the detached claims.
- HTTP checks cover invalid and duplicate credentials, exact origin admission, current scopes, and credential
  refresh. A different subject or client cannot use or delete the session.
- The quota test fills the per-owner and total limits, then verifies that deletion makes room for another session.
- The credential-expiry test keeps the session active with a valid credential and waits for the original stream
  to end at its own deadline. The session remains usable with the valid credential.
- The idle-expiry test leaves a session quiet until its stream closes, then uses Awaitility
  (`org.awaitility:awaitility`) to wait for cleanup to release the reservation.
