## Description

A protected MCP endpoint must establish who is calling before accepting session work. A session identifier names protocol state; it is not a credential. Authentication verifies credentials, while authorization decides which operations that verified caller may perform.

Use the optional `shoostr-mcp` library for this integration.

Here an `AuthenticationExtension` is the request authenticator registered with Shoostr. The mounted `Mcp` provider supplies the SDK server and transport. `McpHttpSecurity` connects admission to a detached `McpIdentity`, and `McpSessionLimits` bounds protocol-session allocation.

The authenticator receives the incoming `Request` and outgoing `Response`. It throws `AuthenticationRequiredException` to request credentials with a `401` challenge when the supplied token is missing or invalid.

This task connects those roles before handling messages. It builds on the basic transport model, but defines the identity and session policy needed by its own example.

Check credentials on every POST, GET and DELETE, and bind the resulting MCP session to that verified identity. `McpHttpSecurity` supplies exact Origin admission, detached identity and a policy before message dispatch. The group callback receives `Extensions`, the built-in scope-configuration object. Select the managed authenticator there with `with(authentication)` so identity extraction receives its authenticated principal. An allowed Origin or a session ID does not authenticate a caller.

This self-contained example uses fixed, development-only Bearer credentials with expiry stored in a local registry.
It does not implement an OAuth provider, cryptographic token verification or external discovery.
Before using private data, replace that lookup with verification of the token's issuer, intended audience, validity and permissions, following the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) and [security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).
The HTTPS metadata URL in the code is illustrative; the example does not host that document or an authorization service.

## Example

The registry creates each credential's actual expiry once, rather than granting a fresh lifetime on every request.
It stores immutable claims in the principal and native transport context, without retaining a Shoostr request, response or mutable provider profile.
The session owner encodes the subject and client separately, keeping scopes and expiry outside the key so refreshed credentials can use the same session.
An application that accepts multiple identity issuers must distinguish the issuer in that key too.

Authentication requires `mcp:access` on every mounted transport method, including GET and DELETE, while the message policy checks incoming JSON-RPC messages before SDK dispatch and requires `tools:read` for tool discovery and calls.
Insufficient scopes produce HTTP 403 with a scope and resource-metadata challenge; these HTTP checks are separate from native tool errors returned by a callback.
Origin admission runs before authentication: requests without Origin are allowed for non-browser clients, and a present Origin must match the single configured browser origin.

The deliberately small limits allow four sessions overall, two per owner and ten seconds of quiescence; they demonstrate policy rather than recommend production capacity.
Initialization and native cleanup both count against capacity, so an expired session can become unavailable before its reservation is released.
The short-lived credential ends an open stream at its fixed expiry without deleting the owner's session; fresh credentials for that owner can still use it.
Idle expiry and explicit session deletion instead end session ownership, with cleanup releasing capacity afterward.

## Test

`TestServer` is the HTTP test fixture: it starts the application on an available loopback port and owns its shutdown.

The SDK client invokes a tool using detached verified claims, while the HTTP checks cover credentials, Origin admission, current scopes, credential refresh and user/client isolation.
The quota checks begin at capacity and use Awaitility (`org.awaitility:awaitility`) to verify recovery after deletion or bounded idle cleanup.
The credential-expiry check uses fresh credentials to keep the session active while the original stream expires, proving that fresh credentials do not extend that stream's deadline.
A separate idle-expiry check leaves its session quiet and waits for the stream to close.
