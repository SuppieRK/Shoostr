## Description

Close the Shoostr application you configure, even if you never start it.
When the server is running, graceful shutdown gives active requests time to finish.
Shoostr releases its owned resources during shutdown. Borrowed components keep their original owner.

Register shutdown callbacks before startup. This example uses one callback to wake waiting
handlers and another to release an application resource after framework cleanup.

| Method        | When it runs                                                                                                                                              |
|---------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `start`       | Called by the owner to compile routes and start the listener. Successful startup freezes registration.                                                    |
| `close`       | Called explicitly or by the JVM shutdown hook. Startup failures after route compilation also invoke it; repeated calls do nothing.                        |
| `beforeClose` | Registered callbacks run in registration order at the start of the first closure, before native graceful shutdown. Use them to signal long-lived work.    |
| `afterClose`  | Registered callbacks run in reverse registration order after framework and extension cleanup. Use them for final disposal of application-owned resources. |

- Construction registers one JVM shutdown hook. Explicit closure removes it when the JVM allows removal.
`start()` adds no hook.
- `Shoostr` implements neither `Closeable` nor `AutoCloseable`. The owner manages its lifetime.
In HTTP tests, the closeable `TestServer` fixture can own shutdown.
- Both callback lists run synchronously on the closing thread, even when the application never started.
- Create a new application to start again after closure.

Return promptly from signaling callbacks so Jetty can begin graceful shutdown. Signal waiting
handlers and let them finish during the drain. Executor ownership determines who stops the pool
and who coordinates any work still running.

| Executor or task                                         | Who handles cleanup                                                                                                                                   |
|----------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| Jetty's platform thread pool                             | Jetty stops it with the server.                                                                                                                       |
| The dedicated virtual-thread executor created by Shoostr | Shoostr closes it.                                                                                                                                    |
| An executor supplied through native configuration        | The caller owns it unless its lifecycle is explicitly registered with Jetty.                                                                          |
| Tasks on a caller-owned executor                         | The caller coordinates them before disposing of resources they still use. Tasks can outlive the Jetty drain. See [endpoint executors](../executors/). |

Whether you can retry startup depends on when it failed. During shutdown, the type of callback failure
determines whether the remaining callbacks in that phase run.

| Failure                                         | What happens                                                                                                                                                           |
|-------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Route compilation is rejected                   | Registration stays open so the owner can correct the routes and retry.                                                                                                 |
| Startup fails after route compilation           | Shoostr closes acquired resources and prevents another startup attempt.                                                                                                |
| A shutdown callback throws a `RuntimeException` | Shoostr collects the failure, runs later callbacks, and still attempts cleanup.                                                                                        |
| A shutdown callback throws an `Error`           | Shoostr stops the remaining callbacks in that phase. After a `beforeClose` error, Shoostr still attempts framework cleanup, then runs the separate `afterClose` phase. |

Shoostr rethrows the first `Error` after cleanup and retains other failures as suppressed exceptions.
If no `Error` occurs, `close()` reports shutdown failures through `IOException`.

## Test

- `TestServer` starts the application from `ShutdownExample.application(...)` on an available loopback port.
  `/ready` responds before cleanup, and closing the fixture runs `dispose` once.
- With a handler waiting, the test closes the application and checks for a `200` response with `stopping` in the body.
  It also verifies final cleanup.
- Closing an unstarted application twice runs each callback once in the documented order. A later start attempt fails.
- An `ApplicationExtension<Object>` throws from `beforeStart()` so the test can verify cleanup and check that a second
  start attempt fails.
- When a signaling callback throws an `Error`, the final cleanup callback runs before `close()` rethrows the error.
