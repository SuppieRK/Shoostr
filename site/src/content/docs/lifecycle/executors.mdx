## Description

Choose where your handlers run. Use Jetty's platform threads, opt into virtual threads for the application,
or give an endpoint its own executor.

| Choice | How to select it | What runs there |
| --- | --- | --- |
| Platform threads | Use the default options. | Ordinary handlers and managed WebSocket callbacks run on Jetty's platform-thread pool. |
| Virtual threads | Call `options.setVirtualThreads(true)` before passing the options to the `Shoostr` constructor. | Ordinary handlers and managed WebSocket callbacks run on virtual threads. |
| Endpoint executor | Pass an `ExecutorService` to the route overload. | The matched work for that endpoint runs on the supplied executor in either application mode. |

Jetty keeps its platform-thread pool for transport work in both application modes. Native callbacks can override
the initial choice through [Jetty pool configuration](../../application/native-configuration/).

Measure your workload before changing execution modes. Virtual threads can help when tasks spend time waiting on
resources with capacity to spare. CPU, database connections and downstream services still have their own limits.
See [Webtide's workload analysis](https://webtide.com/if-virtual-threads-are-the-solution-what-is-the-problem/) and
[Jetty's threading guide](https://jetty.org/docs/jetty/12.1/programming-guide/arch/threads.html).

With an endpoint executor, Shoostr runs request-header hooks and looks up the route before submitting the work.
Matched hooks, admission and the handler run on the selected worker. Use an executor that dispatches asynchronously
or explicitly rejects a submission. Shoostr rejects execution on the submitting thread. Keep the executor available
until the application has closed and its running handlers have finished.

A handoff transfers exclusive access to the live request and response. A `RequestObservation` can carry instrumentation
context across that handoff and later receive a detached `RequestOutcome` at terminal completion.

- Access `Request` and `Response` only on their current owner thread during request handling. Capture detached values
  for work outside that scope.
- Each thread keeps its own thread-local values. Use `RequestObservation.attach()` to install captured context on the
  worker. Shoostr closes the attachment on that same thread so it can restore the previous value.

## Example

`/default` reports whether its handler runs on a virtual thread. `/selected` uses the supplied executor in both
application modes and reads the request ID from the attached context. The example treats the client-supplied ID
as diagnostic data.

- If the executor rejects a submission, Shoostr reattaches observation context on the submitting thread. The example
  returns `503` with the request ID, and the endpoint handler is skipped.
- Observation `close()` restores the original invocation context. `complete(...)` receives the terminal result
  after application cleanup and transport termination.
- A running worker on the caller's pool can outlive application closure. Coordinate outstanding tasks before
  releasing resources they still use. See [application shutdown](../shutdown/).

## Test

`TestServer` starts the application from `ExecutorExample.application(...)` on an available loopback port
and owns its shutdown. The tests check platform and virtual execution, then verify that `/selected` runs on
the named worker in both modes. A second task checks that the worker's previous context was restored,
and the caller can submit work after the application closes.
With the pool stopped, `/selected` returns `503` with the request ID and the terminal outcome records the rejection
