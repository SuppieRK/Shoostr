## Description

An executor chooses where application work runs. Shoostr normally invokes ordinary handlers through Jetty's platform-thread pool, and it can use virtual threads or an endpoint-specific executor instead. The request and response remain live objects with one active application owner, even when that work moves to another thread.

An observation tracks a request across that handoff. `RequestObservation` manages context attachment and cleanup around invocation; `RequestOutcome` is the detached summary supplied at terminal completion. This task first chooses execution and follows that context, then separately demonstrates admission for a long-lived stream.

Select virtual execution with `app.virtualThreads()` before startup when that mode suits ordinary handlers and managed WebSocket callbacks. Jetty retains its platform pool for transport work. Native [pool configuration](../../application/native-configuration/) remains authoritative: fluent call order does not make this convenience selection override native callbacks.

Choose the mode after measuring your request mix and downstream limits.
Virtual threads can help when concurrent tasks wait on resources that have spare capacity, but they do not remove CPU, database connection, or service capacity limits; see [Webtide's workload analysis](https://webtide.com/if-virtual-threads-are-the-solution-what-is-the-problem/).
Jetty's [threading guide](https://jetty.org/docs/jetty/12.1/programming-guide/arch/threads.html) explains native pool sizing and virtual execution.

An explicit endpoint `ExecutorService` selects that endpoint's matched work independently of the application mode.
Pass that executor to the route overload when the matched lifecycle needs a separate worker pool; headers and lookup happen before handoff, while matched hooks, admission and the handler run on its worker.
The executor must dispatch asynchronously rather than running work on the submitting thread, and remains owned by its caller.

Shoostr transfers exclusive request ownership to the selected worker, not permission to share `Request` or `Response` across arbitrary tasks.
Do not retain either object for concurrent or later use, and do not assume arbitrary thread-local values follow the handoff.
For instrumentation context, an observation can explicitly reattach its captured value through `RequestObservation.attach()` and restore each scope on the thread that opened it.

## Example

`/default` reports whether its handler uses a virtual thread, while `/selected` runs on the supplied pool in either mode and reads the attached request identifier.
The observation captures only a string and the context carrier, restoring the original admission scope before handoff and the worker's previous value after invocation.
The identifier is caller-supplied diagnostic data, not a verified identity.

A rejected submission reattaches observation context on the admission thread for error rendering; the example maps it to 503 without invoking the endpoint.
Observation `close()` restores an invocation scope rather than marking the request complete, and `complete(...)` receives the terminal summary separately.
Application closure does not shut down this pool or interrupt a running borrowed worker; coordinate outstanding tasks before releasing resources they still need.

## Compose stream admission

A long-lived handler occupies its task while waiting for events or writing output.
Virtual execution lets idle tasks release their carriers; application admission
still controls how many HTTP exchanges remain active.
Add `resilience4j-bulkhead` to use an application-configured semaphore bulkhead
without introducing another worker pool or Shoostr policy object.

This public `/events` endpoint sends `ready`, waits for its application producer,
then sends the producer's text. `/health` uses the same HTTP server and stays outside
the stream bulkhead. Select `maxConcurrentCalls` for the deployment and set
`maxWaitDuration(Duration.ZERO)` for immediate rejection. The example maps a full
bulkhead to HTTP 503 before starting SSE; this mapping is application policy.

The group callback receives `Extensions`, Shoostr's built-in scope-configuration
object. Its `lifecycle().observe(...)` collector attaches the observation that manages
admission. The observation retains only a detached acquisition flag. Its terminal `complete(...)` releases the permit after both
application cleanup and transport termination, including the framework's final write.
Observation `close()` and handler return happen earlier and cannot release this
HTTP-lifetime permit. A rejected request acquired no permit and releases none.

The caller owns the bulkhead and producer. The producer runs on the HTTP owner and
must return or cooperate with interruption; admission does not forcibly stop Java work.
A disconnected idle client releases capacity only after the handler/transport observes
termination. Coordinate producers during shutdown. This example limits its event route,
not MCP native callbacks, all application traffic or a distributed deployment.
