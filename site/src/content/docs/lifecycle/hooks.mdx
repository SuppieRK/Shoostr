## Description

Run your code at specific points in HTTP processing. Each request hook runs during a named phase, such as
after route matching or before the handler. The phase determines whether the callback can read or change a
live request or response.

Register application hooks on `Shoostr` before startup. For a route or group, register local hooks directly
on the built-in `Lifecycle` supplied for that scope. A terminal observer receives `RequestOutcome`, a detached
summary available after application finalization and transport termination.

The example follows one request from header receipt to completion.

| Method                                         | When it runs                                                                                                                          |
|------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| `onRequestHeaders`    | After request headers become available, before matched-route processing. Application-only, including requests with no matching route. |
| `onRouteMatched`      | After a route matches, before the known body-length check and admission gates. The composed route pattern is available.               |
| `beforeRouteHandler`  | After the known request-size check, before the handler. Throw to reject the request; response streaming is unavailable.               |
| `afterRouteHandler`   | After the matched handler returns successfully; skipped when it throws.                                                               |
| `beforeResponseFlush` | Immediately before each framework-owned response flush. Read-only and repeatable for streaming output.                                |
| `afterResponseFlush`  | After each committed framework-owned response flush. Read-only and repeatable for streaming output.                                   |
| `afterRequest`               | After both application finalization and transport termination. Receives a detached `RequestOutcome`, not a live request or response.  |

- Within each matched phase, local hooks run before application hooks. Each scope keeps its registration order.
- Application terminal observers also see unmatched requests. Local observers apply only to selected endpoints.
- An exception stops the ordinary phase. [Exception handling](../../errors/exceptions/) determines how to
  render a failure before the response commits.

When a handler's response completes normally, both flush callbacks can read the request body. The first read
can happen in `afterResponseFlush`.

| Situation                                        | What happens                                                                                                                                                                                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Finite response without `afterResponseFlush`     | Shoostr discards available unread input after `beforeResponseFlush` and before commitment. If unread input is still unavailable on HTTP/1, the response advertises `Connection: close` and the connection closes.                                                   |
| Finite response with `afterResponseFlush`        | Shoostr keeps input available for the callback. On HTTP/1, it advertises `Connection: close` before commitment if the transport has unread bytes from a known-length body. An unknown-length chunked body triggers the same header even if the handler read it all. |
| Bodyless request or fully read known-length body | The HTTP/1 connection can be reused.                                                                                                                                                                                                                                |
| Streaming response                               | The request body stays readable after an early flush.                                                                                                                                                                                                               |
| HTTP/2                                           | HTTP/2 handles input without a `Connection` header.                                                                                                                                                                                                                 |

Error rendering and framework-generated rejections can discard available request input before the flush, even
with a post-flush callback registered. For those responses, avoid relying on a first body read in that callback.

Retain `RequestOutcome` for work after request completion.

- `statusCode()` gives the committed status, or `0` if the response never committed.
- `applicationFailure()` and `transportFailure()` report the initiating application failure and the terminal
  transport failure separately.
- `routePattern()` contains only the composed registered template, such as `/jobs/{id}`. It is `null` if
  Shoostr selected no endpoint.
- `method()` records the original HTTP method.

Use `routePattern()` to identify endpoints in logs and metrics, with any escaping the output format requires.
Failure objects carry raw diagnostics. Review them before logging, and keep them out of response bodies and metric labels.

Terminal callbacks may run on transport threads where handler thread-local state may be absent. Keep callbacks
nonblocking. Shoostr continues with later terminal observers if one throws a runtime exception.
