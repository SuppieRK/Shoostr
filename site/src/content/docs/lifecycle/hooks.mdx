## Description

A request hook is a callback at a named point in HTTP processing, such as after route matching or before the handler. Application hooks apply across the application; local hooks apply to a selected route or group.

Local configuration is supplied through `Extensions`, a built-in scope-configuration object. Its `lifecycle()` collector registers those callbacks without requiring an installed provider. A terminal observer instead receives `RequestOutcome`, a detached summary after application finalization and transport termination.

This task follows one request through its phases and then examines what remains available at completion. Callback timing determines whether you may read or change a live request or response.

Register application hooks on `Shoostr` before startup. For a route or group, register local hooks through the scope configuration's `lifecycle()` collector. These callbacks configure that scope's request handling directly.
Each method registers a callback for the corresponding request phase:

| Method                                         | When it runs                                                                                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| <code>on<wbr />Request<wbr />Headers</code>    | After request headers become available, before matched-route processing. Application-only, including requests with no matching route. |
| <code>on<wbr />Route<wbr />Matched</code>      | After a route matches, before the known body-length check and admission gates. The composed route pattern is available.               |
| <code>before<wbr />Route<wbr />Handler</code>  | After the known request-size check, before the handler. Throw to reject the request; response streaming is unavailable.               |
| <code>after<wbr />Route<wbr />Handler</code>   | After the matched handler returns successfully; skipped when it throws.                                                               |
| <code>before<wbr />Response<wbr />Flush</code> | Immediately before each framework-owned response flush. Read-only and repeatable for streaming output.                                |
| <code>after<wbr />Response<wbr />Flush</code>  | After each committed framework-owned response flush. Read-only and repeatable for streaming output.                                   |
| <code>after<wbr />Request</code>               | After both application finalization and transport termination. Receives a detached `RequestOutcome`, not a live request or response.  |

Within each matched phase, local hooks run before application hooks, retaining registration order within their scope.
Application terminal observers also see unmatched requests, whose route pattern is absent, while local observers apply only to selected endpoints.
An exception stops the ordinary phase; [exception handling](../../errors/exceptions/) determines how an uncommitted failure is rendered.

During ordinary response completion, request content remains readable in both flush callbacks, including a first read in `afterResponseFlush`.
For an ordinary finite response without an `afterResponseFlush` callback, Shoostr discards available unread input after `beforeResponseFlush` and before committing the response.
If input remains unavailable, HTTP/1 closes the connection and advertises `Connection: close`.

With an `afterResponseFlush` callback, Shoostr preserves input for that callback.
Before committing a finite HTTP/1 response, it advertises closure if some known-length body bytes have not yet been read from the transport.
For a chunked body of unknown length, it conservatively advertises closure even if the handler has consumed the body.
Bodyless requests and fully consumed known-length bodies can retain connection reuse.
Streaming responses keep request input available after an early flush, and HTTP/2 does not use this connection header.

Error rendering and framework-generated rejection responses can discard available request input before flushing, even when a post-flush callback is registered.
Such a callback must not rely on a first body read.

Retain `RequestOutcome` instead of the live request or response: its status is the committed final status, or zero when none was committed, and its separate failure fields distinguish application and transport failures.
Its `routePattern()` contains the composed registered template, such as `/jobs/{id}`, without substituting request identifiers or appending query strings; when no endpoint was selected, it remains `null` rather than exposing the requested path.
Use this registration metadata to identify the endpoint in logs and metrics, applying any escaping your output format requires.
The summary retains the original method and diagnostic failure objects; it does not provide a sanitized log record.
Terminal callbacks may run on transport threads, so do not block them or assume handler thread-local state remains attached.
Runtime failures in one terminal observer do not suppress later observers, but diagnostic failure objects must not become response bodies or metric labels.
